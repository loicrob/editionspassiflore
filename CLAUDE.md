# CLAUDE.md — Éditions Passiflore

## Project overview

WordPress + WooCommerce migration of [www.editions-passiflore.com](https://www.editions-passiflore.com) (currently in PrestaShop) for a French independent publishing house. The site is a book catalog with e-commerce.

- **Theme:** Kadence (parent) + `kadence-child` (all custom code lives here)
- **Custom fields:** Secure Custom Fields (SCF) — **not ACF**, even though the `advanced-custom-fields` plugin is also installed (ignore it)
- **Custom post types / taxonomies:** registered via CPT UI plugin
- **Local environment:** Local by Flywheel (PHP 8.2, Nginx, MySQL)
- **Production hosting:** TBD — possibly Ionos or a better alternative
- **Kadence Blocks plugin:** not installed; decision pending (not needed as long as layouts are built in PHP templates)

### Books → WooCommerce `product` post type

Books are WooCommerce simple products. Cover image = WooCommerce featured image (`get_post_thumbnail_id()`), not an SCF field.

**SCF group `group_69c7d37956f1c` "Informations du livre" — onglets et champs clés :**

> ⚠️ `titre` supprimé de SCF → utiliser `post_title` / `$product->get_name()`. Ne jamais faire de `meta_query` sur `titre`.

| Onglet SCF | Champs principaux |
|---|---|
| Informations principales | `sous-titre`, `distinctions` (repeater), `extrait` (file PDF → id) |
| Contributions | `contributions` (repeater : `type`, `assignation`, `fiche-auteur` → auteur id, `nom_de_l'auteur`) ; `nom_de_plume`, `illustration_de_couverture` |
| Autres images | `quatrieme_de_couverture`, `tranche`, `autres` (repeater → image id) |
| Caractéristiques | `nouveaute`, `date_de_parution` (**retourne `Ymd`**), `disponibilite`, `public`, `nombre_de_pages`, `type`, `type_de_reliure`, `langues` (checkbox) |
| ~~Livres associés~~ | **Onglet supprimé de SCF** → désormais géré globalement (voir « Groupes de livres » plus bas) |
| Liens et fichiers | `lien_place_des_libraires`, `articles_de_presse`, `videos`, `podcasts` |
| Avis | `avis_des_lecteurs`, `avis_des_libraires` (repeater : titre, auteur, date_de_publication, avis) |

**Points d'attention :**
- `date_de_parution` : `return_format = Ymd` → parser avec `DateTime::createFromFormat('Ymd', $val)`
- `contributions` → `fiche-auteur` est un `multi_select` taxonomy (retourne id)
- Champs supprimés (ne plus utiliser) : `mots-cles`, `meta_description`, `resume`, `collection`, `thematique`, `format`, `isbn`, `dimensions`, `prix_ht`, `prix_ttc`, `livre_numerique`, `version_grands_caracteres`, `version_litterature_generale`
- **Livres associés supprimés de SCF** (gérés désormais en global, voir « Groupes de livres ») : `autres_ouvrages_de_la_suite` + `ordre_dans_la_suite` (supprimés sans remplacement), `autres_ouvrages_de_la_serie` + `ordre_dans_la_serie`, `vous_aimerez_aussi`, `traductions`. ⚠️ L'onglet « Livres associés » reste à supprimer manuellement dans l'admin SCF (Custom Fields).

**Avis lecteurs — deux sources qui coexistent** (rendu par `inc/book-single-tabs.php`, section « Avis des lecteurs ») :
- **Avis curés par l'éditeur** : repeaters SCF `avis_des_lecteurs` / `avis_des_libraires` (sous-champs `titre`, `auteur`, `date_de_publication`, `avis`), saisis depuis le back-office → sous-bloc « Sélection de l'éditeur ».
- **Avis déposés par les visiteurs** : avis WooCommerce natifs (commentaires WP, table `comments`), **sans note par étoiles**, ouverts à tous (nom requis, email retiré), modérés avant publication (`comment_moderation = 1`) → sous-bloc « Avis des lecteurs du site » + formulaire. Nécessite `comment_status = open` sur le produit (réglé en masse sur les livres existants).
- « Avis des libraires » reste une section SCF distincte.
- Anti-spam à la soumission : honeypot + piège temporel (timestamp signé HMAC) via `passiflore_avis_spam_check` sur `preprocess_comment`, rejet *avant* enregistrement, modérateurs exemptés. Pas de plugin anti-spam installé (Antispam Bee envisageable si besoin).
- **Réponses de l'éditeur** : commentaires-réponses (`comment_parent`) saisis depuis wp-admin. Affichées publiquement sous l'avis sur la fiche livre **uniquement si** le commentaire-réponse porte le meta `_pf_reply_public` (case « Réponse publique ? » sur l'écran d'édition du commentaire, gérée par `Passiflore_Mes_Avis`). Toujours visibles par le client dans son compte. Rendu fiche via `passiflore_avis_public_reply()`.
- **Suivi dans le compte client** (`inc/class-mes-avis.php`, `Passiflore_Mes_Avis`) : endpoint `/mon-compte/avis-laisses` (libellé menu « Avis laissés ») listant les avis du client connecté avec statut (publié / en attente / non retenu), édition (repasse en modération) et suppression (corbeille + meta `_pf_user_deleted` pour distinguer du refus éditeur) via AJAX (`pf_avis_edit`, `pf_avis_delete`). **Contrainte :** un avis n'est rattaché à un compte que par `user_id` → seuls les avis déposés en étant **connecté** sont traçables (email retiré du formulaire, donc avis d'invités non rattachables).
- **Notifications email au client** (fonctions dans `inc/book-single-tabs.php`) : à la validation de son avis (`transition_comment_status`) et lorsque l'éditeur y répond (`wp_insert_comment`, anti-doublon via meta `_pf_reply_notified`).

**Custom WooCommerce product meta** (post meta, managed by `Passiflore_Bookshelf`):
- `_book_pages` — spine thickness calculation (sync with `nombre_de_pages`)
- `_book_width_mm`, `_book_height_mm`

**`format_groupe` taxonomy** (CPT UI, managed by `inc/modifier-produit.php`):
- Constrained to a single term per product
- Each term = a book title that exists in multiple formats (classique, grands-caractères, numérique…). All format editions of the same book share the same term.

| Relation | Stockage | Sens |
|---|---|---|

**Conventions clés :**

Pour les taxonomies, le terme est posé sur **toutes les éditions** de chaque œuvre membre (lookup inverse direct depuis n'importe quelle édition).

- **Ordre = drag-reorder uniquement** : pas de numéro de tome, **pas de badge « Tome X »** (la plomberie `show_ordre`/`resolve_ordre` du bookshelf a été retirée).
- Rendu fiche livre : `passiflore_get_livres_lies_sections()` (`inc/book-single-tabs.php`) lit ces sources puis ré-aiguille vers le format consulté via `passiflore_ids_in_format()`, et affiche chaque section avec `[passiflore_etagere ids="..."]`.

### Offre « version numérique » à l'achat d'un livre papier (`inc/numerique-offer.php`)

Incite à acheter la version **numérique** d'un ouvrage quand le client prend sa version **papier** (format *classique* ou *grands caractères*), à tarif réduit. Tout le back (option, logique, admin, hooks panier, endpoints AJAX, rendu case fiche) vit dans `inc/numerique-offer.php` ; deux JS front (`assets/js/numerique-offer.js`, `numerique-cart-nudge.js`).

**Réglage** — écran admin **Boutique (WooCommerce) → « Offre version numérique »** (`add_submenu_page` sous le parent `woocommerce`, capability `manage_woocommerce`, sauvegarde nonce + PRG sur `load-{$hook}`, calquée sur `book-groups-admin.php`). Positionné **entre « Clients » et « Codes promo »** via `pf_numerique_reorder_submenu` (hook `admin_menu` prio 100, réinsère juste avant `coupons-moved`) — l'ordre d'un sous-menu WooCommerce dépend de l'ordre d'insertion, peu fiable, d'où le réordonnancement explicite plutôt que le paramètre `$position`. Option globale **`pf_numerique_offer`** (non-autoload) : **deux entrées** (`classique`, `grands-caracteres`), chacune `{ mode, value }` avec `mode ∈ {disabled, percent, fixed, free}`. **Dormant par défaut** : option absente → mode `disabled` → aucune UI, aucun impact panier.

**Modèle** — le format source est lu sur `pa_format_particulier` (classique = **aucun** terme ; sinon slug `grands-caracteres`) ; le numérique compagnon = membre du même `format_groupe` avec `pa_format_particulier = numerique`. Helpers (point d'entrée unique **`pf_numerique_offer_for( $physical_id )`** → `{numerique_id, source, mode, value, regular, price}` ou `null`) : `pf_numerique_source_format()`, `pf_numerique_companion_id()`, `pf_numerique_price()` (parse la virgule décimale FR, clamp % à 100). `value` = % de réduction (mode `percent`) ou prix € (mode `fixed`) ; base = `get_regular_price()` du numérique.

**Fiche livre** — `pf_numerique_render_offer_checkbox( $id )` echoée dans `woocommerce/content-single-product.php` juste après le prix (`.bs-hero__info`). La case pilote (via `numerique-offer.js`) l'attribut **`data-pf_add_numerique`** sur le bouton `.bs-hero__cart` : le JS cœur WooCommerce (`add-to-cart.js`) **recopie tous les `data-*` du bouton dans la requête AJAX d'ajout** → aucun endpoint custom. Côté serveur, `woocommerce_add_to_cart` (`pf_numerique_maybe_add_companion`) lit `$_REQUEST['pf_add_numerique']` et ajoute le numérique avec la cart-item meta **`pf_numerique_companion`** = ID du papier (garde anti-récursion sur cette meta). Amélioration progressive : sans JS, le papier s'ajoute normalement, l'offre n'est simplement pas appliquée.

**Offre masquée quand le numérique est déjà au panier** — il y est vendu à l'unité, la reproposer n'a pas d'objet. ⚠️ **Masquage côté CLIENT (`numerique-offer.js` → classe `.is-in-cart`), jamais au rendu** : la fiche livre est une page **cacheable**, un rendu conditionné au panier ferait servir l'état d'un visiteur à tous les autres (le premier arrivé avec le numérique au panier ferait disparaître l'offre pour tout le monde). Le HTML servi reste donc identique pour tous — vérifié : après rechargement, l'offre est bien dans la réponse serveur et c'est le JS qui la retire. Source de vérité : le **mini-panier du header**, seul bloc de la page qui reflète le panier réel même derrière un cache (c'est un fragment WooCommerce, restauré depuis sessionStorage puis rafraîchi en AJAX) ; chaque article y porte un `a.remove[data-product_id]`, comparé au `data-pf-numerique-id` posé sur le `<label>`. Un `MutationObserver` sur le parent du fragment (celui-ci étant *remplacé*, pas modifié) rejoue la synchro à chaque changement de panier — l'offre revient donc d'elle-même si on retire le numérique. Repli volontairement **ouvert** (pas de mini-panier → offre visible) : la montrer à tort est sans conséquence, `pf_numerique_maybe_add_companion` refusant déjà le doublon (`pf_numerique_product_in_cart`) ; la cacher à tort ferait perdre une vente. La case est décochée en même temps qu'elle est masquée, sinon elle resterait armée sous une offre invisible.

Une **infobulle** (composant partagé `.pf-numerique-tip`, styles dans `style.css`, comportement dans `assets/js/pf-tooltip.js`) suit **le prix barré** (prix normal du numérique) : texte via `pf_numerique_offer_sentence()` (ex. « Pour l'achat d'un format classique, la version numérique est à -70 %. » — le format cité est la source de l'offre : classique / grands caractères). Sur la fiche, `numerique-offer.js` appelle `window.pfTooltip.wire( tip, { preventClick: true } )` — `preventClick` car l'icône vit dans le `<label>` (sinon le clic cocherait la case). Survol/focus gérés en CSS ; `pf-tooltip.js` ajoute l'ouverture au tap/clavier, la fermeture au clic extérieur/Échap, et **recale la bulle horizontalement** (`translateX`) pour qu'elle reste dans le `.site-container` le plus proche (bulle ancrée à droite, elle passerait sinon sous le bord gauche). **La même infobulle est réutilisée dans l'encart panier** (cf. plus bas).

**Prix de la ligne numérique** — `woocommerce_before_calculate_totals` (`pf_numerique_apply_prices`) : tant que le papier référencé est au panier, `set_price( offer.price )` sur la ligne compagnon ; s'il est retiré → on ne touche à rien = **prix plein** (« repasse au prix plein »). Idempotent (recalcul depuis le prix régulier, jamais depuis un prix déjà modifié). Fonctionne en **panier/checkout blocs (Store API)**, qui respecte le prix de ligne serveur.

**Encart de rappel — panier en blocs** — pas de hook PHP de rendu : `numerique-cart-nudge.js` (chargé sur `is_cart()`, dép. `wp-data`) interroge l'endpoint **`pf_numerique_cart_offers`** (livres papier au panier dont le numérique n'est pas encore ajouté) au chargement + à chaque variation du store `wc/store/cart`, injecte un encart `.pf-numerique-nudge` (`.pf-panel`) au-dessus du bloc panier ; « Ajouter » → **`pf_numerique_add_companion`** → rechargement. Nonce `pf_numerique_cart`. Deux points d'attention sur ce retour :
- **Confirmation par relais `sessionStorage`** (clé `pfCartToast`, relevée **et effacée** au chargement par `cart-toast.js`) : l'encart rechargeait la page **sans le moindre retour**, `WC()->cart->add_to_cart()` n'émettant aucune notice (c'est WooCommerce qui l'ajoute depuis ses propres gestionnaires de formulaire/AJAX, jamais depuis le panier). Une notice serveur (`wc_add_to_cart_message()`) aurait suffi à afficher quelque chose, mais avec la formulation et l'icône d'une *notice* : cet ajout doit ressembler à tous les autres ajouts au panier (caddie, titre en semibold italique). Le toast ne pouvant pas être affiché avant le rechargement, l'encart passe donc le relais. Le titre transmis est celui du **produit ajouté** (`added_title`, « … (numérique) ») et non le libellé affiché par l'encart (« Version numérique de *Titre* »), qui ne se recolle pas au gabarit de phrase des toasts panier.
- **Le rechargement nettoie l'URL** (`add-to-cart`, `quantity` retirés, puis `location.replace`) : un `reload()` rejouerait l'URL courante telle quelle, donc un `?add-to-cart=` encore présent dans la barre d'adresse — le livre papier était ajouté **une deuxième fois** (constaté en test). Chaque ligne « Version numérique de *Titre* : *prix* » porte **la même infobulle** que la fiche (markup `.pf-numerique-tip` construit en JS, phrase `tip` fournie par l'endpoint `pf_numerique_cart_offers`, câblée via `window.pfTooltip.wire()` après insertion dans le DOM).

**Mention « Offre »** — `woocommerce_get_item_data` (`pf_numerique_cart_item_data`) ajoute une ligne « Offre : version numérique liée à l'achat du livre papier » sous la ligne numérique (panier + checkout, classique **et** Store API — le Store API expose `item_data` via ce filtre). Masquée si le papier a été retiré.

**Mini-panier Kadence (dropdown header)** — override `woocommerce/cart/mini-cart.php` (calqué sur le cœur WooCommerce 10.0.0, seul le `<li>` par article change : petite carte cliquable, voir plus bas). Là, on **ne montre pas** la « variation » (ligne Offre) : à la place, la ligne de prix affiche le **prix régulier barré** (`.pf-mini-old-amount`, style dans `style.css`) accolé au prix promo. Mécanisme : un drapeau global **`pf_in_mini_cart`** posé entre `woocommerce_before_mini_cart` / `woocommerce_after_mini_cart` cible ce seul contexte → `pf_numerique_cart_item_data` s'abstient, et `pf_numerique_mini_cart_price` (sur `woocommerce_cart_item_price`) **reconstruit** le prix depuis l'offre (`prix promo` + `<del>` régulier). ⚠️ On reconstruit plutôt que d'accoler au HTML reçu : selon le moment du rendu du mini-panier (ex. `?wc-ajax=get_refreshed_fragments`), l'objet produit ne porte pas encore le prix posé par `before_calculate_totals` → sans reconstruction, la ligne afficherait le prix plein. L'override préserve ces actions `before`/`after_mini_cart` à l'identique (seul point d'ancrage du mécanisme), donc rien à changer côté offre numérique.

**Numérique = vendu à l'unité** — filtre `woocommerce_is_sold_individually` (`pf_numerique_sold_individually`) : tout produit `numerique` est `sold_individually` (indépendant de l'offre — remisé ou non). Effet : quantité verrouillée à 1 et **sélecteur de quantité retiré du panier/checkout en blocs** (le Store API expose alors `quantity_limits.editable = false`, `max = 1` → le composant `.wc-block-components-quantity-selector` n'est pas rendu). Acheter plusieurs fois le même fichier n'a pas de sens.

**Articles du mini-panier en petites cartes cliquables** — chaque `<li class="woocommerce-mini-cart-item">` est une `.pf-card` (+ `.pf-card--static` si le produit n'a pas de permalien) : lien étiré `.pf-card-link` vers la fiche livre, titre en `.pf-card-title` (rougit au survol de la carte entière via la règle globale déjà utilisée par les cartes événement). `display:block` (override du `display:flex` par défaut de `.pf-card`, dans `style.css`) conserve la mise en page interne héritée de WooCommerce/Kadence (image flottante, `.quantity` en `padding-left`). Bordure fine ajoutée (le dropdown a déjà un fond blanc) ; le bouton **×** de suppression reste cliquable au-dessus du lien étiré via un `z-index` dédié. `.pf-card-link` (positionnement absolu) et `position: relative` sur `.pf-card` sont désormais des règles **partagées** dans `style.css` (auparavant dupliquées dans `events.css` pour les cartes événement, seul autre usage du lien étiré).

### Connexion / création de compte (`inc/account-auth.php` + override `woocommerce/myaccount/form-login.php`)

WooCommerce n'a **pas** de page de connexion distincte : « Mon compte » est une page unique dont le contenu dépend de la session (déconnecté → `form-login.php`). Le cœur y affiche connexion et inscription **côte à côte**, ce qui fait hésiter le visiteur (deux boîtes aux champs quasi identiques, empilées sur mobile) et contredit le bouton du header, qui promet « Connexion ». Remplacé par **un seul panneau à la fois**, connexion par défaut, création de compte à un clic. Cohérent avec le fait que la **commande invité est activée** : créer un compte n'est jamais un passage obligé pour acheter, la page sert d'abord aux clients qui reviennent.

**L'état vit dans l'URL** (`/connexion` vs `/creer-un-compte`), lu au rendu par `pf_auth_current_state()` pour poser `.is-register` sur `#customer_login`. Ce n'est pas cosmétique : les formulaires postent vers l'URL courante et WooCommerce, en cas d'erreur (email déjà pris, mot de passe refusé), se contente d'empiler une notice et de **re-rendre cette même URL** — si l'état n'y figurait pas, le visiteur retomberait sur le formulaire de connexion avec un message d'erreur orphelin. Les deux bascules sont donc de **vrais liens** (`data-pf-auth-target`) : tout fonctionne sans JavaScript ; `assets/js/account-auth.js` ne fait qu'éviter le rechargement, et **réécrit l'URL via `history.replaceState`** (en reprenant le `href` du lien, pas en reconstruisant l'URL) pour que le POST suivant parte au bon endroit.

- **URL dédiées, servies sur place** : règle de réécriture `^connexion/?$` et `^creer-un-compte/?$` → `index.php?page_id=<myaccount>&pf_auth=login|register`. La requête résout sur la **vraie page compte** — `is_account_page()` est authentiquement vrai, donc noindex, notices et gestionnaires de formulaire fonctionnent normalement ; **rien n'est simulé**. Seule l'adresse affichée change. `?action=register` reste supporté (forme historique, et cible d'une éventuelle 301 déjà en cache navigateur).
  - **Dépendances** : uniquement des API du cœur WordPress (`add_rewrite_rule`, `page_id`, `redirect_canonical`, `query_vars`) + un seul appel public WooCommerce, `wc_get_page_id('myaccount')`. **Moins exposé aux MAJ WooCommerce que l'override `form-login.php`**, qui lui demande une comparaison de version.
  - **`redirect_canonical` neutralisé** quand `pf_auth` est présent : sinon WordPress voit que l'URL demandée diffère du permalien de la page interrogée et renvoie un 301 vers `/mon-compte` — l'URL dédiée disparaîtrait aussitôt.
  - **Flush unique auto-cicatrisant** (option `pf_auth_rw_version`, signature incluant l'ID de la page compte → changer de page compte régénère les règles). Même motif que `pf_carte_rw_version`. ⚠️ `preg_quote()` volontairement **absent** du slug : depuis PHP 7.3 il échappe le tiret, et la table de réécriture devient illisible (`^creer\-un\-compte/?$`) — les slugs sont des littéraux du fichier, pas une entrée utilisateur.
  - **Deux garde-fous** (`template_redirect` priorité 1) : visiteur **déjà connecté** sur une URL d'auth → page compte (sinon il verrait son tableau de bord sous l'adresse « /connexion ») ; et **repli 404** si les règles manquent en base (migration, option `rewrite_rules` purgée) → redirection vers la page compte dans le bon état. Le cœur ne relit jamais en direct les règles ajoutées par `add_rewrite_rule()`, d'où ce filet — même gotcha que les catalogues PDF.
  - **Pas de contenu dupliqué** : la page étant en noindex, Rank Math n'émet aucun canonical — les deux URL sont simplement invisibles pour les moteurs.
  - **Après connexion/inscription → page compte en UN seul saut** (filtres `woocommerce_login_redirect` / `woocommerce_registration_redirect`). ⚠️ `wp_nonce_field()` ajoute d'office un `_wp_http_referer`, dont WooCommerce se sert comme destination post-authentification : sans ces filtres on repart vers `/connexion`, puis le garde-fou « déjà connecté » corrige — soit deux redirections, et surtout une **destination finale qui dépend du garde-fou**. S'il ne s'exécute pas (plugin sortant plus tôt sur `template_redirect`, page servie depuis un cache), le visiteur reste sur `/connexion` en étant connecté. Les filtres ne réécrivent que nos deux URL d'authentification : une connexion déclenchée depuis une fiche livre ramène toujours sur la fiche livre (vérifié).
  - **Restauration bfcache** (`account-auth.js`) : le bouton Précédent ré-affiche le HTML mémorisé **sans consulter le serveur**, donc avec l'état d'authentification d'avant (formulaire de connexion, bouton « Connexion ») alors que la session a pu s'ouvrir entre-temps. Aucun garde-fou PHP ne peut le corriger — aucune requête n'a lieu. `pageshow` + `event.persisted` → `location.reload()`.
  - **Après déconnexion → `/connexion`** (filtre `woocommerce_logout_default_redirect_url`), au lieu de la page compte où le visiteur voyait le formulaire de connexion sous une adresse annonçant son espace client. On corrige la **destination** à la source plutôt que d'ajouter une redirection conditionnelle « déconnecté sur /mon-compte → /connexion » : celle-ci porterait sur le chemin qui sert aussi `mot-de-passe-perdu` (cible du lien de réinitialisation envoyé par e-mail), pour un bénéfice purement cosmétique — la page étant `noindex`, il n'y a aucun enjeu de contenu dupliqué. Décision actée : `/mon-compte` reste une adresse valide pour le formulaire (comportement natif WooCommerce), seule la destination après déconnexion change.
  - ⚠️ **Les points d'entrée du site doivent viser `pf_auth_url('login')`, pas `wc_get_page_permalink('myaccount')`** — sinon un bouton libellé « Connexion » dépose le visiteur sur `/mon-compte` et l'URL dédiée ne sert jamais. Trois aujourd'hui, tous conditionnés à `! is_user_logged_in()` (connecté, c'est bien la page compte) : bouton du header et entrée du tiroir mobile (`inc/header-hooks.php`), bouton « liste de lecture » invité de la fiche livre (`inc/class-reading-list.php`). Chacun retombe sur la page compte si `pf_auth_url()` n'existe pas.
    - **Le bouton « liste de lecture » invité ne navigue plus au clic** : `shelf-bookmarks.js` intercepte (`preventDefault`) et lève un toast « Veuillez vous connecter pour pouvoir ajouter *Titre* à votre liste de lecture. » + action **« Se connecter » → `/connexion`**. Fermeture automatique à **7 s** (plus que les 5 s des confirmations d'ajout/retrait : il y a davantage à lire ET un bouton à atteindre) et **une seule invitation à la fois** (re-cliquer n'empile rien tant que la précédente n'est pas quittée). Le `<a href>` reste un vrai lien : c'est le repli sans JS **et** la cible de l'action du toast — donc `pf_auth_url('login')` est toujours l'unique source de l'URL.
- **Pourquoi un override de template ici** (alors que la seule bascule aurait pu se faire par hooks + CSS) : les besoins sont markup-level — `<h1>`, libellés en placeholder, attributs de clavier mobile. ⚠️ Override calqué sur le cœur **`@version 9.9.0`** : à comparer lors d'une MAJ majeure de WooCommerce (même obligation que `cart/mini-cart.php`). Tous les `do_action` et champs nonce d'origine sont préservés.
- **Libellés en placeholder** (convention du site, cf. bloc newsletter : ` *` suffixé sur les champs obligatoires, rien sur les facultatifs), mais **`<label>` conservés en `.screen-reader-text`** — un placeholder n'est pas un libellé accessible (il disparaît à la saisie). Les champs Prénom/Nom (facultatifs, greffés par `pf_register_name_fields()` dans `inc/recommendations.php`) suivent la même convention.
- **Titres en `<h1>`** : la page compte déconnectée n'en avait **aucun**. Le panneau masqué l'est en `display:none` → hors arbre d'accessibilité et hors ordre de tabulation, donc un seul `<h1>` exposé et pas de champ invisible captant l'autocomplétion.
- **Claviers mobiles** : `inputmode="email"` + `autocapitalize="none"` + `autocorrect="off"` + `spellcheck="false"` sur l'identifiant de connexion — **pas `type="email"`**, ce champ acceptant aussi l'identifiant WordPress (généré depuis l'email, réglage `woocommerce_registration_generate_username`), que la validation HTML5 rejetterait. Le champ email d'inscription garde `type="email"`. `autocapitalize="words"` sur Prénom/Nom, `enterkeyhint="go"` sur les mots de passe.
- **Layout (`account.css`)** : le titre vit **hors** de la carte, seul le formulaire est encadré (`.pf-panel`) — WooCommerce pose son propre cadre gris sur `form.login`/`form.register` en (0,2,1), ré-imposé en (0,3,1) avec les tokens du composant, sans `!important`. ⚠️ `.woocommerce` est en **flex** (layout nav + contenu du compte connecté) et `.woocommerce-notices-wrapper` en est un autre enfant : `.pf-auth` prend `flex: 0 0 100%` pour occuper sa ligne, sinon une notice d'erreur courte tiendrait à côté du formulaire. Le plafond de largeur (`--pf-auth-width`) est porté par le **panneau**, pas par l'item flex (un `max-width` sur l'item réduirait sa taille hypothétique et autoriserait à nouveau la cohabitation) ; les notices sont calées sur la même colonne via `:has()`.
- **Plein écran** : `min-height: calc(100svh - var(--pf-auth-top))` + `align-content: center` sur la zone → header + panneau occupent au moins la hauteur du viewport, panneau centré verticalement, **le haut du bloc newsletter tombant exactement sur le bas de l'écran**. Pour ça il faut aussi neutraliser la `margin-bottom` de `#primary.content-area` (48 px) — elle s'ajouterait sous la zone et repousserait la newsletter sous la ligne de flottaison ; scopée par `:has(.pf-auth)`. La marge **haute** du même élément est conservée (respiration sous le header) : elle est déjà comptée dans `--pf-auth-top`, mesuré depuis le haut du viewport. `svh` et non `dvh`/`vh`, même choix que le hero d'accueil (stable face au repli de la barre iOS). **`--pf-auth-top` = distance réelle entre le haut du viewport et le début de la zone** : CSS ne sait pas l'exprimer, car `--pf-sticky-offset` ne compte que les barres **collantes** (80 px) alors que la zone démarre à ~184 px — le bandeau bêta, non collant, occupe le haut du header, plus les 32 px de `margin-top` de `#primary.content-area` (`--global-md-spacing`, seul ancêtre porteur d'espacement, vérifié en parcourant la chaîne). `account-auth.js` mesure donc la position réelle et écrase la variable en inline ; la valeur déclarée en CSS (`sticky-offset + md-spacing`) est le repli sans JS, exact une fois le bandeau bêta retiré. Le `gap` du conteneur est mis à 0 (le wrapper de notices, **même vide**, forme une ligne flex → un gap complet s'insérerait au-dessus du panneau), l'espacement notice → panneau étant porté par la notice via `:has(*)`.
- **Placeholder qui s'efface au focus** : WooCommerce pose `[placeholder]:focus::-webkit-input-placeholder { opacity: 0 }` avec un fondu retardé d'une demi-seconde, sur tout `form .form-row` (règle identique dans `woocommerce.css` **et** dans le `woocommerce.min.css` de Kadence, toutes deux en 0,4,2) — comportement isolé sur le site, où les placeholders tiennent jusqu'à la saisie. Neutralisé **globalement dans `style.css`** (tous les formulaires WooCommerce classiques : compte, connexion/inscription, adresses, mot de passe perdu), en préfixant `body` → (0,4,3), ce qui l'emporte quel que soit l'ordre de chargement des feuilles, sans `!important`. ⚠️ Règle **isolée**, à ne jamais grouper avec la version standard `::placeholder` : un navigateur qui ne connaît pas l'un des pseudo-éléments d'une liste de sélecteurs invalide la règle **entière**.
- **« Rester connecté »** : Kadence impose `bold` + 90 % + palette5 sur tout `form .form-row label` (0,2,2) ; retour à la voix de texte courante en (0,3,0), case et libellé alignés (`display:flex; align-items:center`) avec un `gap`.

### Header collant — vrai `position: sticky` (`inc/header-sticky.php` + `style.css`)

Kadence ne pose jamais `position: sticky`. Il rend **deux** headers (`#main-header` ordinateur / `#mobile-header`), n'en affiche qu'un par media query, et bascule celui qui est visible en `position: fixed` au scroll (`navigation.min.js`, `initStickyHeader`). Deux bugs mesurés le 2026-07-28, tous deux issus de cette architecture :

1. **Bande morte à 1024 px pile** — le JS bascule à `1024 <= innerWidth`, le CSS à `min-width: 1025px`. À cette largeur exacte (iPad 9,7"/mini en paysage, fenêtre d'ordinateur courante), le JS rend collant le header **desktop, masqué**, pendant que le header mobile — seul visible — reste dans le flux : plus rien ne colle.
2. **Seuil empoisonné au franchissement du point de bascule** (zoom navigateur, redimensionnement, devtools ancrés, rotation de tablette) — Kadence recalcule son seuil avec `getOffset()` = `rect.top + scrollY` sur un élément qui peut **déjà** être en `position: fixed`, et lit donc `top + scrollY`. Le seuil devient la position de scroll du moment : le header ne recolle plus qu'en dessous, et remonter le laisse défiler avec la page **jusqu'au rechargement**. Rien ne se voit au moment du redimensionnement, la casse n'apparaît qu'en remontant — d'où l'impression d'aléatoire (candidat sérieux au bug intermittent signalé le 2026-07-17).

**Correctif : `position: sticky` sur `#masthead`** (`style.css`), sticky JS de Kadence débranché (`inc/header-sticky.php`, filtres `theme_mod_header_sticky` / `theme_mod_mobile_header_sticky` → `'no'`).

- **C'est `#masthead` qu'on colle**, pas `.site-header-inner-wrap` : le parent de celle-ci (`#main-header`) est aussi haut qu'elle, un sticky y serait libéré au premier pixel. `#masthead` a pour parent `#wrapper` (toute la page) **et contient les deux headers** → un seul élément collant couvre toutes les largeurs : il n'y a plus de point de bascule dans la logique de collage.
- **Forcé par filtre, pas par le customizer** : versionné avec le thème, donc identique en local et en prod sans manipulation au déploiement. ⚠️ Conséquence : les réglages « En-tête collant » du customizer n'ont plus d'effet.
- **`top` = `calc(var(--pf-adminbar) + var(--pf-banner-h, 0px))`** — barre d'admin WP + bandeau bêta (sticky `top:0`). `--pf-banner-h` est mesurée par un **primer inline** placé juste après le bandeau (`inc/beta-banner.php`) — avant le premier paint, sinon un rechargement avec scroll restauré peindrait le header à cheval sur le bandeau — puis tenue à jour par un `ResizeObserver` (`beta-banner.js`) qui couvre d'un coup le repli du bandeau, le changement de largeur et l'arrivée des polices. **Tout est temporaire avec le bandeau** : le repli `0px` rend la règle juste d'office le jour où il est retiré. Repli **sans JS** : `:root { --pf-banner-h: 85px }` dans `beta-banner.css` (plus grande hauteur observée) — sans lui le header se collerait à `top:0`, donc **derrière** le bandeau (`z-index` supérieur), et disparaîtrait.
  - ⚠️ Le `ResizeObserver` est livré **après** l'événement `resize`, sur lequel `--pf-sticky-offset` est calculé → sans rappel, une rotation de téléphone laissait l'offset une mesure en retard (17 px entre 390 et 500 px de large). D'où `window.pfRefreshStickyOffset` (exposée par `recherche-globale.js`, appelée depuis le RO du bandeau).
- **Verre dépoli allumé en permanence, sans classe d'état ni JS** : le header colle dès le premier pixel de scroll, ses deux états n'étaient donc que « crème opaque » vs « la même crème à 90 % + flou ». Au repos rien ne passe derrière lui — le flou n'a rien à flouter, la translucidité se composite sur un fond uni : **`rgb(246,241,234)` contre `rgb(245,240,232)`**, soit 1 à 2 valeurs sur 255. La bascule `.item-is-fixed` (que posait le sticky JS) disparaît donc sans rien coûter visuellement, et **aucun `IntersectionObserver` sentinelle n'a été nécessaire**.
- **Ce qui NE change pas** (vérifié avant migration) : `#masthead` était **déjà** `position: relative` → aucun changement de bloc conteneur pour les descendants absolus (mini-panier, sous-menus) ; aucun descendant en `position: fixed` (les panneaux de la recherche globale sont déplacés dans `<body>` par leur JS) ; `#wrapper` est en `overflow: clip`, qui **ne casse pas** sticky (contrairement à `hidden`) ; le `z-index: 20` de `#masthead` est inchangé (le `1200` de `.item-is-fixed` ne jouait qu'à l'intérieur de son propre contexte d'empilement, pas contre le contenu de la page).
- **Effets de bord vérifiés** : `navigation.min.js` reste chargé (la version « lite » n'est substituée que si `enable_scroll_to_id` est faux, or il vaut `true` par défaut) → tiroir mobile et sous-menus intacts, `initStickyHeader` ne trouve plus d'élément et n'enregistre aucun écouteur. Le scroll d'ancre de Kadence (`getTopOffset`) retomberait à 0, mais les deux seuls jeux d'ancres du site (fiche livre, fiche événement) le court-circuitent déjà via `body.no-anchor-scroll`, et **aucune entrée de menu n'est une ancre** (vérifié en base) → sans effet. Le fond blanc que Kadence pose sur `#masthead` est généré **hors** du bloc CSS gardé par ces options : il reste en place.
- Le détecteur temporaire du bug intermittent (`assets/js/sticky-debug.js` + `inc/sticky-debug.php` + son `require`) a été **supprimé** avec cette migration : il guettait `.kadence-sticky-header` / `.item-is-fixed`, qui ne sont plus émis.
- **Vérifié** (headless, avant/après) : 4 pages × 3 largeurs × 2 positions de scroll → header `sticky` calé à 72/68 px partout, `--pf-sticky-offset` identique à l'avant (152,375 / 148,484 px) ; bande header **pixel pour pixel identique** au repos comme défilée, sauf aux 4 captures à 1024 px défilées — c'est la correction. Écarts résiduels = bruit de capture, confirmé par un run de contrôle après/après (l'animation arc-en-ciel du « Cliquez ici » du bandeau). Franchissements du point de bascule (×3, avec retours en arrière) : collant à chaque étape. Rechargement à scroll restauré, bandeau replié/redéplié, `body.admin-bar` (72 → 104 px), largeurs 1400/1025/1024/1023/768/500/390 : conformes. **Sans JavaScript** (`Emulation.setScriptExecutionDisabled`) : header collant — ce qu'il n'était **jamais** avant, le sticky de Kadence étant purement JS — et jamais masqué par le bandeau (écart 0 à 17 px).

**Logo du header ordinateur, fluide entre 1025 et 1065 px** (`style.css`, `#main-header .site-branding img`) — la rangée du header est une **grille `1fr auto 1fr`** : `[logo | menu | recherche + compte + panier]`. Le track du logo est plafonné par sa propre largeur (200 px, réglage `logo_width`), donc en dessous de ~1060 px c'est le **menu** qui encaissait le manque de place : il passait à deux lignes et emportait la loupe de recherche sous « Accueil / Présentation… », tandis que « Mon compte » (deux mots, donc sécable — contrairement à « Connexion », d'où un symptôme visible **uniquement connecté**) se coupait en deux lignes. Le logo, lui, ne bougeait pas.

- **Formule mesurée, pas devinée** : par dichotomie sur la largeur de logo à chaque viewport, la largeur maximale qui garde tout sur une ligne suit `largeur de mise en page − 883` (142 px à 1025, 200 px à 1085 — **pente 1:1**). D'où `clamp(135px, calc(100vw - var(--scrollbar-offset, 0px) - 887px), 200px)` : 4 px de marge, plafond à la taille nominale.
- ⚠️ **Calibré PANIER REMPLI.** Son compteur fait passer le bloc panier de 43 à 66 px et décale le seuil de 20 px — une première calibration panier vide reculait le problème sans le régler (menu replié dès qu'un article était au panier). La largeur du badge **ne dépend pas** du nombre d'articles (66 px de 1 à 99, vérifié) : « panier non vide » est donc bien le pire cas. La formule ne dépend que de la largeur, **jamais du contenu du panier** — sinon le logo changerait de taille à chaque ajout.
- ⚠️ **`100vw` inclut la barre de défilement**, ni les media queries ni la mise en page ne le font. Sans correction, un Windows à barres classiques (~15 px) calculerait un logo 15 px trop large et le menu se replierait quand même. `--scrollbar-offset` est tenu à jour par Kadence (script inline `window.innerWidth − clientWidth`, émis **avant** le header → pas de saut).
- ⚠️ **`max-width: none` obligatoire** : tout plafond en % rendrait la main à la grille, dont le track `1fr` se rabat sur sa part égale du reste — **plus petite que la formule** dès qu'on remonte (192 px à 1100, alors que 200 y tient). Piège rencontré : avec `max-width: 100%` la règle « marchait » (rien ne se replie) mais rétrécissait le logo sur toute une plage qui n'avait aucun problème.
- **Espace insécable dans « Mon compte »** (`inc/header-hooks.php`, `"Mon\u{00A0}compte"`) : seul libellé du header en deux mots, donc le seul sécable — « Connexion » ne l'a jamais fait, d'où un symptôme visible **uniquement connecté**. Ceinture, en complément du logo fluide : le libellé reste d'un bloc même si la rangée devenait plus dense. Le lien du **tiroir mobile** (même fichier) garde l'espace normale : pleine largeur, aucun risque de coupure.

**Header MOBILE — même traitement** (`@media (max-width: 767px)`, `#mobile-header .site-branding img`) : `[logo | loupe + panier + burger]`. Le déclencheur n'est pas la largeur seule mais le **panier rempli** — sous ~355 px le burger débordait de la rangée pendant que la loupe venait toucher le logo. Mesuré dans ce pire cas, en exigeant 12 px de respiration logo↔loupe : 128 px à 320, 148 px à 340, 150 px dès 360 — pente 1:1 là encore, d'où `clamp(120px, calc(100vw - var(--scrollbar-offset, 0px) - 196px), 150px)`. Borné à ≤767 px : au-delà le header mobile passe à 180 px de logo (`logo_width` tablette) et la place ne manque plus. **La pastille « β » du bandeau bêta est hors de cause** : elle déborde de la boîte du logo sans l'élargir (vérifié — `brandRight` inchangé qu'elle soit affichée ou non).

- **Vérifié** (panier rempli, pastille bêta affichée) : mobile 320→767 px, aucun débordement, écart logo↔loupe ≥ 17 px ; ordinateur 1025→1440 px **dans les deux états de connexion**, aucun repli de menu, loupe alignée, compte sur une ligne, logo 138 px à 1025 croissant jusqu'à 200 px à 1087. Bande header inchangée (bruit de capture seul) à 1400, 1024 et 500 px.

### Notices WooCommerce → toasts (`inc/wc-notices-toast.php` + `assets/js/wc-notices-toast.js` + `assets/js/wc-block-notices-toast.js`)

WooCommerce imprime ses messages (succès / erreur / info) dans un `.woocommerce-notices-wrapper` posé en tête de la zone de contenu : bandeau pleine largeur, loin du geste qui l'a déclenché, qui pousse la page vers le bas et qu'un visiteur ayant scrollé ne voit pas. Ils partent désormais dans le composant toast du site (`window.pfToast`), comme les retours de la liste de lecture, de la newsletter et des avis.

**Deux systèmes de messages, deux contrôleurs**, un seul rendu (le toast) et une seule règle : *on ne reprend que ce que le CSS masque*, c'est-à-dire des **conteneurs** de notices — jamais un message ancré à un endroit précis de la page.

- **Périmètre : des conteneurs, rien d'autre.** Restent en place, volontairement : les `.woocommerce-info` rendus **hors** wrapper (« Vous avez déjà un compte ? » du tunnel, bloc coupon, panier vide) ; les **erreurs de champ** du tunnel en blocs (`.wc-block-components-validation-error`, store `wc/store/validation`), ancrées sous le champ fautif — c'est là que vit le message du code promo refusé, qui n'est **pas** une notice ; et les bannières composées **à demeure** dans une étape du tunnel (`.wc-block-checkout__no-payment-methods-notice`, même classe de bannière mais hors conteneur), qui décrivent un état permanent.

**A. Notices classiques** (`assets/js/wc-notices-toast.js`) — le `.woocommerce-notices-wrapper` de toujours.

- **1 notice = 1 toast** : une notice d'erreur multiple est un `<ul class="woocommerce-error">` de plusieurs `<li>`, chacun étant un `wc_add_notice()` distinct → un toast distinct, fermable séparément. Un type inconnu (plugin greffé sur `woocommerce_notice_types`) est traité comme une info plutôt qu'ignoré : le wrapper étant masqué, il serait sinon **perdu**.
- **Wrapper injecté sur les pages en blocs** (`render_block` sur `woocommerce/cart` et `woocommerce/checkout`, `inc/wc-notices-toast.php`) : ces pages n'en rendent aucun — seul le bloc « Notices de la boutique » appelle `woocommerce_output_all_notices()`, et il n'est sur aucune des deux. Une notice mise en file pendant un chargement de page (`?add-to-cart=` sur `/panier`, retour de redirection d'une passerelle) y restait **invisible** et ne ressortait que sur la page suivante. Fait en code plutôt qu'en insérant le bloc dans l'éditeur : le contenu des pages n'est pas versionné et ne survivrait pas à leur recréation. ⚠️ Rien sur les endpoints `order-pay` / `order-received` — le bloc Checkout s'y efface au profit du shortcode classique, qui imprime déjà ses notices via `before_woocommerce_pay`. Le bloc reste une alternative valable : la règle CSS couvre déjà son enveloppe `.wc-block-store-notices`.
- **1 notice = 1 toast** : une notice d'erreur multiple est un `<ul class="woocommerce-error">` de plusieurs `<li>`, chacun étant un `wc_add_notice()` distinct → un toast distinct, fermable séparément. Un type inconnu (plugin greffé sur `woocommerce_notice_types`) est traité comme une info plutôt qu'ignoré : le wrapper étant masqué, il serait sinon **perdu**.
- **Le CTA devient un bouton d'action** : WooCommerce place l'appel à l'action en tête de message (`<a class="button">`, ex. « Voir le panier ») → sorti du texte et rendu en action du toast (`.pf-btn--primary.--sm`). ⚠️ **Sauf s'il pointe vers la page courante** (« Voir le panier » sur la page panier) : le lien est retiré du texte dans tous les cas — un bouton au fil du message n'a pas sa place dans un toast — mais aucune action n'est créée, elle ne ferait que recharger la page.

**B. Notices React des blocs Panier/Commande** (`assets/js/wc-block-notices-toast.js`, dép. `wp-data`) — conteneurs `.wc-block-components-notices` (bannières) et `.wc-block-components-notices__snackbar` ; les deux formes portent la même classe `.wc-block-components-notice-banner` (+ `is-error`/`is-success`/`is-warning`/`is-info`). **Deux capteurs, parce qu'aucun ne couvre l'autre :**

- **Le store `core/notices`** (erreur de paiement, échec de soumission, coupon retiré, échec d'ajout au panier depuis un bouton de bloc) : on prend la notice et on l'en **retire aussitôt** (`removeNotice`, ce que fait déjà son bouton « rejeter »). Sans ce retrait, une notice à identifiant fixe (`add-to-cart`, `wc-payment-error`) resterait en place et **une deuxième tentative identique n'afficherait plus rien**. Surtout, certaines n'ont **aucun conteneur pour les rendre** : un échec d'ajout au panier est publié en contexte **`wc/all-products`**, dont le conteneur n'existe que sur le bloc « Tous les produits », absent du panier — vérifié, WooCommerce l'y perd purement et simplement. Les reprendre ici les rend visibles (gain net sur le comportement natif). Liste des contextes dans le fichier.
- **Le DOM** (`MutationObserver`, une passe par frame) : les erreurs renvoyées par la Store API dans la réponse panier (article devenu indisponible, prix modifié) sont passées au conteneur en **props** (`additionalNotices`) et ne transitent jamais par le store. Diff entre deux passes plutôt que mémoire cumulative → une notice qui disparaît puis revient redonne un toast, un simple re-rendu de React non. Bannière groupée (résumé + `<ul>`) → un toast par `<li>`, comme côté classique.
- ⚠️ **On ne retire jamais un nœud du DOM de React** (il le supprimerait à son tour plus tard → `removeChild` sur un nœud disparu) : les conteneurs sont masqués en CSS, on se contente de recopier. Et **anti-doublon de 2 s** sur `statut|texte` : si React peint la notice avant qu'on ne l'ait retirée du store, les deux capteurs la voient. Une vraie répétition demande un aller-retour utilisateur, bien plus long.

**Commun aux deux :**

- **Durées / sévérité** : erreur = **0** (fermeture manuelle — un message bloquant ne doit pas s'effacer tout seul, et il n'a alors pas de barre de progression) ; succès, avertissement et info gardent le défaut du composant (5 s, minuteur en pause au survol/focus). La sévérité passe dans la **couleur de l'icône** (variantes `.pf-toast--success/--error/--warning/--info`, tokens `--pf-success/-danger/-warning/-info`), pas dans un aplat de fond : un bandeau rouge pleine largeur en bas d'écran serait plus agressif que la notice d'origine. `error` passe aussi le toast en `role="alert"` — c'est ce que portait le `<ul class="woocommerce-error">`.
- **Amélioration progressive** : les conteneurs ne sont masqués que par `html.pf-notices-js`, posée par un **primer inline** (`wp_head` prio 1 — idiome du bandeau bêta et de `.pf-cat-js`). Sans JavaScript la classe n'existe pas → les notices classiques s'affichent normalement à leur place (les règles de calage des notices d'`account.css` restent donc utiles), et il n'y a de toute façon pas de blocs. ⚠️ Le voile doit tomber **avant le premier paint** : les contrôleurs vivent en pied de page, sans lui la notice serait peinte à sa place d'origine puis retirée — flash **et** saut de layout.
- **Coût nul hors notice** : primer et scripts ne sont émis que si `wc_notice_count() > 0` **ou** sur une page en blocs (panier / commande), où une notice React peut surgir à tout moment sans rien en file au chargement. La file est interrogée dans `wp_head`, donc avant que `wc_print_notices()` ne la vide au rendu. Angle mort assumé hors pages en blocs : une notice classique ajoutée **pendant** le rendu (après `wp_head`) n'est pas vue → elle s'affiche dans son bandeau d'origine. Repli correct, jamais une page cassée.
- **Vérifié** (headless, site local) : identifiants refusés sur `/connexion` → toast rouge persistant `role="alert"`, wrapper vidé et masqué ; ajout au panier non-AJAX (`?add-to-cart=`) → toast vert avec l'action « Voir le panier » extraite ; **JavaScript coupé** → bandeau d'origine intact ; wrapper synthétique (3 `<li>` + info avec bouton + type inconnu) → 5 toasts dans l'ordre, rien de perdu. Côté blocs : `?add-to-cart=` sur `/panier` → toast (avant, message perdu jusqu'à la page suivante) ; notice `wc/all-products` (échec d'ajout) → toast, alors que WooCommerce ne l'affiche nulle part ; erreur `wc/checkout/payments` → toast ; répétition du même message après un délai utilisateur → nouveau toast ; bannière groupée (2 `<li>`) injectée dans le conteneur → 2 toasts, bannière restée masquée ; « Aucun moyen de paiement disponible » → **reste en place, aucun toast**.

### SEO — désindexation des événements passés anciens (`inc/seo-events.php`)

Rank Math n'a pas de règle « noindex par date » ; ce fichier la pose via ses filtres. Un événement **terminé depuis plus de `PF_EVENT_SEO_STALE_AGE`** (constante, `-6 months`) passe en **noindex** et sort du **sitemap**, **sauf** s'il porte le flag SCF `evenement_marquant` (alors indexé quel que soit son âge). Futur / en cours / passé récent : indexé (défaut Rank Math, non touché). Contexte : ~97 % des événements sont d'anciens passés (fiches à faible valeur SEO + mauvaise UX pour un visiteur qui y atterrit depuis Google).

- **`pf_event_seo_stale( $event_id )`** : `true` si `evenement_marquant` non coché **et** `_EventEndDate` (heure locale TEC, `Y-m-d H:i:s`) antérieur à `strtotime( PF_EVENT_SEO_STALE_AGE )`. Comparaison à la maille du mois → l'écart de fuseau (local vs UTC) est négligeable, pas de conversion.
- **Balise `<meta robots>`** : filtre `rank_math/frontend/robots` (dernier filtre robots de Rank Math, `class-paper.php`) → `$robots['index'] = 'noindex'` sur la fiche périmée. Rendu au vol, pas de cache.
- **Sitemap** : le sitemap Rank Math ne relit **pas** ce filtre robots — son SQL exclut les posts dont la post-meta `rank_math_robots` contient « noindex ». Notre noindex étant calculé au vol (non stocké en meta), un **second** filtre `rank_math/sitemap/entry` (retour `false` = URL exclue) retire les fiches périmées.
  - ⚠️ **L'objet passé est une ligne SQL brute (`stdClass`), PAS un `WP_Post`** — `Post_Type::get_posts()` fait un `$wpdb->get_results()` avec un `SELECT` de colonnes. Tester par propriété (`isset( $o->post_type, $o->ID )` + `$o->post_type === 'tribe_events'`), **jamais `instanceof WP_Post`** (échouerait silencieusement → aucune exclusion).
  - ⚠️ **Cache** (fichiers dans `uploads/` + transients) : après déploiement du code, purge obligatoire pour régénérer — `\RankMath\Sitemap\Cache::invalidate_storage()` (bootstrap WP), ou `wp rank-math sitemap generate`, ou ré-enregistrer les réglages du sitemap, ou éditer un post (invalide alors le seul cache du type concerné).
  - ⚠️ **Sous-sitemaps vides possibles** : l'index pagine sur le compteur **brut** d'événements (le filtre `entry` ne réduit pas ce compteur), donc `tribe_events-sitemapN` peut renvoyer 0 URL quand ses ~200 candidats sont tous périmés. **Sans effet** (sitemaps vides tolérés par Google, tous les événements à garder restent présents). Un filtrage au niveau SQL (`sitemap/get_posts/where` **+** `sitemap/post_count/where`, tous deux obligatoires pour ne pas perdre d'entrées) rendrait l'index exact mais dupliquerait la logique `stale` en SQL — non retenu (simplicité).
- **Type « Événements » dans le sitemap** : activé côté Rank Math **en ligne uniquement** (`pt_tribe_events_sitemap`) — **pas en local** (l'index local ne liste que pages + produits, donc le filtre sitemap y est un filet inerte). Sans ce réglage, les événements restent découvrables par le maillage interne (archive `/evenements`).
- **Portabilité** : aucune valeur d'environnement en dur (ni domaine ni slug) — uniquement `is_singular('tribe_events')`, les meta `evenement_marquant`/`_EventEndDate` et les hooks Rank Math. Rien à changer au déploiement.
- **Interaction avec le déréférencement global (site en test)** : tant que WordPress est réglé « Demander aux moteurs de ne pas indexer » (`blog_public = 0`), tout le site est noindex et ce filtre est redondant. Au repassage en public, le défaut redevient `index` et le filtre reprend seul son rôle (anciens → noindex, récents → index), sans réactivation.
- **Vérifié** (headless, site local) : périmé non marquant → `noindex, follow` ; récent → `index, follow` ; périmé **marquant** → `index` (bascule temporaire de `evenement_marquant` sur un événement périmé, puis restauration). 1282/1323 événements concernés. Sitemap (activé en local) après purge du cache : **1324 → 42 URLs**, ancien exclu / récent conservé.

**Canonical des vues d'archive TEC — slash final retiré** (même fichier, filtre `rank_math/frontend/canonical`) : sur `/evenements` (+ vues `liste`/`mois`/`carte`, mois daté, pagination), Rank Math dérive le canonical de `get_post_type_archive_link( 'tribe_events' )`, que TEC filtre (`Tribe__Events__Main::event_archive_link`) pour y **forcer un slash final**. La structure de permaliens du site étant `/%postname%` (sans slash), `redirect_canonical` renvoie `/evenements/` en **301** vers `/evenements` → le canonical pointait vers une URL qui redirige. Le filtre applique `untrailingslashit()`, gardé par `$wp_rewrite->use_trailing_slashes` (si la structure passait un jour en mode « avec slash », le filtre s'efface) et scopé aux vues d'archive (`tribe_is_event_query() && ! is_singular()`). Sans effet sur la pagination (`/evenements/page/2` reste auto-référent) ni sur les fiches événement.

**Rappel — canonical absent = page `noindex`, par conception de Rank Math** : `includes/frontend/class-head.php` retire la balise canonical dès que `robots['index'] === 'noindex'` (noindex + canonical étant contradictoires pour Google). Sur ce site, cela concerne : les 1282 événements périmés (règle ci-dessus), les archives `product_tag` (réglage `tax_product_tag_robots`), les termes vides (`noindex_empty_taxonomies`), la recherche, les 404, et **panier / commander / mon-compte** (forcés en `noindex, follow` par le module WooCommerce de Rank Math, `includes/modules/woocommerce/class-woocommerce.php::robots()`, qui débranche au passage le `wc_page_noindex` du cœur WooCommerce). Ce n'est donc **pas** un défaut à corriger. Audit complet du 2026-07-25 : 2270 URL publiques balayées, 0 canonical en double, 0 canonical non auto-référent hors vues d'archive événements.

### Authors → `auteur` custom taxonomy

Registered via CPT UI. SCF field group `group_69c2ca10aa3d2` ("Fiche d'auteur"):

| Field name | SCF type | Notes |
|---|---|---|
| `nom` | text | Required. Last name or organisation name |
| `prenom` | text | |
| `genre` | radio | `feminin` or `masculin` — returns label |
| `photo` | image (id) | Required |
| `biographie_synthetique` | textarea | Required |
| `biographie_complete` | wysiwyg | Required |

The `auteur` taxonomy term name, slug and description are auto-synced from SCF fields via hooks in `inc/auteurs.php`. The standard WordPress name/slug/description fields are hidden in the admin form.

**Relations de termes `auteur` sur les livres — synchronisées depuis SCF (`inc/auteurs.php`) :**

Les livres ne référencent leurs auteurs que via le repeater SCF `contributions → fiche-auteur` (IDs en postmeta), **jamais** par de vraies relations de termes WordPress → sans correctif, tous les termes `auteur` ont `count=0`. Conséquence SEO : Rank Math les traite comme « vides » et (a) **`noindex_empty_taxonomies=on` → passe les fiches auteurs en `noindex`**, (b) `tax_auteur_include_empty=off` → les **exclut du sitemap**. Les pages auteurs étaient donc désindexées ET absentes du sitemap alors qu'elles affichent des livres.

- **Correctif** : `passiflore_sync_auteur_terms()` pose la vraie relation `wp_set_object_terms( $product, …, 'auteur', false )` (mode remplacement = miroir fidèle du SCF, nettoie les orphelines) à partir de **`passiflore_get_product_author_ids()`** (`inc/author-books-grouping.php`) — exactement l'ensemble que la page auteur affiche via `passiflore_product_ids_by_auteur_terms()`. Hooks `acf/save_post` @20 (contributions déjà écrites) **+** `save_post_product` (import/quick edit).
- **Toute contribution `fiche-auteur` compte, quel que soit le rôle** : `type` (auteur, photographies, traduction, illustrations, dessins, notes, textes) est un simple *label* — une personne créditée sur un livre dans **n'importe quel** rôle est un auteur (décision actée 2026-07-24). `passiflore_get_product_author_ids()` et `passiflore_product_ids_by_auteur_terms()` ne filtrent donc **pas** sur `type` (élargi le 2026-07-24 : ces deux helpers partagés servent aussi recherche, recommandations, « ajouter par auteur » admin, page auteur — cohérent partout). Le filtrage par rôle spécifique reste possible via le param `role=` de `[passiflore_etagere]` (indépendant). Un terme `auteur` sans **aucune** contribution garde count=0 → reste noindex (correct : page vide).
- **Additif, idempotent, réversible** : ne touche pas au SCF (source de vérité), rejouable sans effet de bord.
- **Backfill** : `passiflore_backfill_auteur_terms()` (tous les livres), déclenché une fois par environnement au premier `admin_init` (flag option `pf_auteur_terms_synced`). Le compteur devient exact → Rank Math ré-indexe les fiches et les ajoute au sitemap (⚠️ purger le cache sitemap après, cf. section SEO événements). **Après une ré-importation d'auteurs/livres** : si l'import ne déclenche pas `save_post_product`, relancer la synchro (supprimer l'option `pf_auteur_terms_synced`, ou `wp eval 'passiflore_backfill_auteur_terms();'`).
- **Vérifié** (local) : backfill 229 livres → **77/80 termes count>0** (dont un contributeur au seul rôle photographe) ; page auteur `follow, noindex` → `index, follow` ; `auteur-sitemap.xml` apparaît avec **77 URLs**.

## Bookshelf feature (`Passiflore_Bookshelf`)

A 3D book-on-shelf display system.

**Constantes de sizing (`class-bookshelf.php`) :**

| Constante | Valeur | Rôle |
|---|---|---|
| `SCALE` | `1.2` px/mm | Facteur de conversion mm → pixels |
| `DEFAULT_HEIGHT_MM` | `210` | Hauteur par défaut |
| `DEFAULT_WIDTH_MM` | `140` | Largeur par défaut |
| `MM_PER_PAGE` | `0.08` | Épaisseur de dos par page |
| `MIN_SPINE_MM` | `10` | Épaisseur minimum du dos |
| `MAX_SPINE_MM` | `60` | Épaisseur maximum du dos |
| `PASSIFLORE_RED` | `#c62836` | Couleur de fallback pour les dos sans couverture |

**Calcul de l'épaisseur du dos :**
1. Si la photo de dos existe : largeur de l'image en mm (calculée depuis ses proportions)
2. Sinon si `nombre_de_pages` renseigné : `spine_mm = pages × 0.08`
3. Sinon : `spine_mm = MIN_SPINE_MM (10mm)`
4. Clamp : `max(10, min(60, spine_mm))`
5. Conversion : `spine_px = round(spine_mm × SCALE × mode_scale)` (mode_scale = 1.5 en mode `spines`, 1.0 en mode `covers`)

**Key CSS variables:**
- `--book-h`, `--book-w`, `--spine-w` — set inline per book
- `--plank-color-top: #d4c4a8`, `--plank-color-front: #c0ad8e`, `--plank-color-dark: #a89474`
- `--wall-color: #f5f0e8`, `--frame-color: #e0d8cc`
- `--pf-obl` (`0.3249`, `0.2309` sous 767px) — **angle de fuite partagé par les deux modes**, voir ci-dessous
- `--pf-backcover` (`4px`) — épaisseur des plats, voir « Quatrième de couverture » plus bas

Le `min-height` qu'il alimentait valait `book-h + 52` pour une hauteur naturelle de `book-h + 73` : il était **inerte** (forcé à 0 sur les 146 rangées du catalogue → 0 changement de hauteur). **Mobilier de l'étagère — responsive depuis le 2026-07-28** (`bookshelf.css`)

Tout le mobilier était **absolu** : le mobile héritait des 40px de padding et de la planche de 44/58px du bureau sur un écran 3,6× plus étroit (33 % d'un écran de 390px consommés avant le premier pixel de livre).

- **`--pf-plank-inset` tient trois nombres qui n'en font qu'un** : marge latérale de la planche, retrait **arrière** de son dessus (`clip-path`), et padding latéral de la rangée exprimé en `calc(var(--pf-plank-inset) * 2)`. Mesuré à 1400px : arête arrière du bois à 41px du bord, premier livre à 41px — le pied du livre est **calé sur l'arête de sa planche**, par construction. Les désaccorder l'en décolle. Le hero (`book-single.css`) impose 64px : **l'invariant est un minimum (`padding >= 2 × retrait`), pas une égalité**.
- **Sous 767px** : `--pf-plank-inset` 8px, `--plank-h` 32px (40 avec chevalet), `--plank-front` 6px, `gap` 12px, `padding-top` 18px. Largeur disponible à 390px : **262 → 310px**. Écart planche → livre du dessous : **92 → 54px**, soit **34 % → ~20 %** de la hauteur d'une rangée (29 % sur ordinateur). Les 92px étaient 52px de **zone morte** (la part de la boîte de la planche que remonte son `top: calc(-0.9 * var(--plank-h))`, invisible) + 40px de padding — réduire `--plank-h` agit sur les deux sans casser la construction (le pied du livre reste à 85 % de la bande de bois).
- ⚠️ **Le `padding-top` ne se réduit qu'en shelves + COUVERTURES.** En **scroll**, le rayon rogne au padding-box et `computeRevealShift` ne peut redescendre le livre saisi que de la valeur du padding-bas (3px) : ce dégagement haut est le seul rempart. En **dos**, la bascule au survol fait monter l'encre de **55px** pour les livres les plus profonds (17px seulement en couvertures) — il faut garder 69px de dégagement, et le gain y serait marginal (4 % de la hauteur de page, les rangées étant dominées par la hauteur des dos). Le **hero** (32px) et l'**étagère de recommandations** (64px, badge flottant) sont exclus explicitement plutôt qu'en pariant sur l'ordre de chargement des feuilles.
- **Point de rupture 768 → 767px** (règle 6 du design system) : à 768px pile, l'ancien `max-width: 768px` appliquait encore l'angle de fuite mobile.

**Réduction des livres — UN facteur par étagère, calé sur le p95** (`bookshelf.js`, `FIT_PERCENTILE`)

`fitBookshelf()` réduisait **livre par livre** : chaque livre trop large sortait exactement à la largeur disponible, donc un album de 360 mm et un roman de 220 mm rendus **identiques** (36 livres sur 146 à 390px), à côté de leurs voisins restés à taille vraie. Les tailles relatives — tout l'intérêt d'une étagère — disparaissaient.

- Le facteur se cale sur le **p95** des empreintes et non sur la plus grande : un unique très grand format (*Tabaco y oro*, 360 mm, 2,2× la médiane) imposerait sa réduction à tout le catalogue. Les ~5 % au-dessus restent **écrêtés individuellement** — sans quoi ils déborderaient, `#wrapper` étant en `overflow: clip`.
- **Plage utile [0,95 ; 1,00] et rien d'autre** : sous 0,95 le facteur sature à 1 et seul le nombre d'écrêtés augmente, c'est-à-dire qu'on réintroduit le défaut corrigé. À 390px — 1,00 → médian 138px, 1,45 livre/rangée ; **0,95 (retenu) → 173px, 1,04 livre/rangée, 10 écrêtés** ; 0,90 → aucun gain. Le curseur arbitre entre « les livres restent grands » et « ça redevient une étagère » : **p95 protège la taille des livres mais laisse le catalogue mobile à ~1 livre par rangée** ; p97–p99 le densifie.
- **Inerte au-dessus de 768px** (facteur 1, aucun écrêtage) sans media query : vérifié, 1 235 livres comparés à ≥768px, 0 écart géométrique.
- ⚠️ Le percentile porte sur les livres **affichés** : filtrer le catalogue peut donc changer la taille de tous les livres. Cohérent en interne ; l'alternative serait de calculer la référence sur l'ensemble du catalogue et de la passer depuis le PHP.

**Assise du livre sur la planche avec chevalet de prix — `--pf-chevalet-reserve`**

Le chevalet occupe une bande **devant** le pied du livre (`padding-bottom` sur `.pf-book--has-price`, mode couvertures) : le livre est donc assis d'autant plus en arrière dans le bois. Cette réserve étant absolue et la planche mobile ayant été amincie, l'assise était tombée à **3px sur 40 (8 % de la profondeur du bois) à 390px, contre 19 sur 58 (33 %) sur ordinateur** — le pied du livre affleurait l'arête arrière de la planche.

- **Deux valeurs à faire varier ensemble**, d'où le token : sous 767px, réserve 30 → **22px** (le chevalet n'y mesure que 21px, contre 24 sur ordinateur) et `--plank-h` du cas chevalet 40 → **44px**. L'assise revient à **33 %**, exactement le rapport de l'ordinateur, pour seulement 3,6px de plus sur l'écart entre deux rangées.
- L'étiquette « À paraître » se **dérive** de la réserve (`calc(var(--book-h) + var(--pf-chevalet-reserve) + 4px)`, soit les 34px d'origine sur ordinateur) au lieu d'être un troisième nombre à resynchroniser à la main.
- Formule utile : assise = `0.9 × --plank-h − (réserve + 3px de padding-bas de rangée)`.

**Taille du livre SAISI en mode dos — `--pf-reveal-scale`**

Le mode dos dessine tout **1,5× plus grand** (`mode_scale`, pour que les titres verticaux restent lisibles). Une fois le livre retourné, cette taille vaut pour sa **couverture** : `fitBookshelf()` ne regardant que la largeur du **dos** (empreinte au repos), rien ne bornait la couverture dévoilée — mesuré **693px pour 308px disponibles** à 390px sur le plus grand format du catalogue (*Tabaco y oro*), donc débordement de l'étagère (rogné en mode scroll, déversé sur les rangées voisines en shelves). Défaut préexistant, indépendant du facteur p95.

- **`computeRevealShift()` plafonne l'agrandissement de la saisie** à ce qui tient dans le rayon : `scale = min(1.1, (largeur du rayon − 2×14px) / (cover + spine))`, posé en `--pf-reveal-scale` sur le livre. Le dos **au repos n'est pas touché** — c'est sa lisibilité qui justifie le 1,5×.
- ⚠️ **Ce facteur vit à TROIS endroits qui doivent rester d'accord** : la `transform` de saisie, le **`perspective-origin`** (terme `(scale − 1) × --book-h`, qui repère le haut du volume agrandi — c'était le `0.1 × --book-h` en dur) et le calcul de `--reveal-dx`/`--reveal-dy`. Désaccordés, l'atterrissage ne retombe plus sur la cavalière du mode couvertures.
- **Vérifié** : à 390px le facteur tombe à 0,481 (catalogue) / 0,577 (accueil), l'encre peinte **ouverture de couverture comprise** fait 321px pour un rayon de 340 (contre 693 avant), rien n'est rogné ; à 1400px le facteur reste à 1,1 et tout est inchangé. **L'invariant d'atterrissage tient au millième** : rapport bandeau/épaisseur = 0,2309 à 390px et 0,3249 à 1400px, soit exactement `--pf-obl` des deux côtés.

**Dos rendus à 1,2× au lieu de 1,5× sous 767px — `--pf-spines-scale`**

Le `mode_scale` de 1,5 (PHP) rend les dos trop hauts sur un téléphone. Le viewport étant inconnu du serveur, le correctif est un facteur CSS lu par le JS — **le point de rupture reste donc en CSS**, jamais dupliqué en JS.

- ⚠️ **Il s'applique à TOUT l'intérieur du dos**, sans quoi la mise en page de `spine_layout()` ne tiendrait plus : dimensions (`bookshelf.js`), **corps du texte** (le PHP émet désormais `--pf-spine-fs` au lieu d'un `font-size` en dur, multiplié en CSS), **marges** de `.pf-spine-generated` (dont le total reste synchronisé avec `SPINE_PAD_Y`) et **logo**. Tout étant multiplié par le même nombre, le calcul du PHP reste juste **par similitude**.
- ⚠️ **Scopé `.pf-bookshelf--spines`** : les dos générés existent aussi en mode couvertures (livres sans photo de tranche), où ils ne doivent pas rétrécir.
- **Vérifié** à 390px : dos médian 23 → 18px, hauteur max 535 → 428px, corps 12 → 9,6px, **0 titre qui déborde**, catalogue en vue dos 7 278 → 4 718px (−35 %) ; à 1400px tout est identique (facteur 1). Effet de bord utile : 29 % des livres seulement restent écrêtés à la saisie, contre ~50 % avant.

**Retour au repos depuis la saisie — `.pf-book--releasing`**

Le repos transitionne en **0,3s** avec une autre courbe que la saisie (**0,5s**). Tant que le livre saisi n'était que 1,1× plus grand, l'asymétrie ne se voyait pas ; depuis que `--pf-reveal-scale` peut le réduire, le retour cumule un changement d'échelle de ~1,7× et une longue course horizontale, et se lisait comme un claquement.

- **Classe transitoire posée par `bookshelf.js`** : le CSS ne sait pas distinguer « je quitte la SAISIE » de « je quitte la BASCULE », qui doit rester à 0,3s. Le délai de commutation de `perspective` suit la même durée — à 0,3s il tomberait au milieu d'un retour de 0,5s, donc en plein mouvement.
- **`--pf-reveal-dur` (0,5s, `.pf-bookshelf`) = source unique de la durée du DÉVOILEMENT**, jumelle de `--pf-release-dur`. Elle pilote les six transitions du vol : rotation du volume, course de la caméra, voile de profondeur du dos, ombrage du bloc de pages, épaississement des deux plats. Vérifié : à `6s`, les six passent bien à 6000 ms et le livre atterrit à sa géométrie normale (caméra −6114 px, couverture 206 px, perspective 6000 px). **N'inclut PAS** `REVEAL_DELAY_MS` (700 ms, `bookshelf.js`) : c'est le temps de survol exigé *avant* que le livre bouge, pas une durée d'animation. ⚠️ L'ombrage `.pf-book-pages::before` est la seule transition du cycle qui servait aux **deux sens** avec un seul nombre (le style d'arrivée fournit la durée) : elle est désormais dédoublée — `--pf-release-dur` sur la règle de repos (l'arrivée du retour), `--pf-reveal-dur` sur la règle de saisie — sinon l'ombrage se désolidarise du vol dès que les deux durées diffèrent. Vérifié indépendantes : dévoilement à 6s + retour à 0,5s → toutes les transitions du retour à 500 ms.
- **`--pf-release-dur` (0,5s, `.pf-bookshelf`) = source unique de la durée du retour.** Consommée par les trois règles de `.pf-book--releasing`, par le délai de `visibility` de la couverture, **et par `bookshelf.js`**, qui en déduit combien de temps garder la classe (`cssDurationMs()` + `RELEASE_MARGIN_MS`). ⚠️ Le minuteur JS **ne règle pas la durée de l'animation** — piège vécu : allonger le seul minuteur ne ralentit rien, il ne fait que garder le livre au-dessus de ses voisins après son retour. Pour observer l'animation au ralenti, changer **`--pf-release-dur`** (ex. `15s`), rien d'autre ; ça marche aussi en direct depuis les devtools, sur `.pf-bookshelf--spines`. La marge doit rester **petite et positive** : la classe doit survivre à la transition (elle porte le z-index) mais pas au-delà (le livre resterait au-dessus de ses voisins au repos), et la transition ne démarre pas à l'armement du minuteur mais au recalcul de style suivant.
- ⚠️ **Posée dans `onLeave()` ET dans `closeTouchBook()`** : sur téléphone le livre se referme par un tap à côté, pas par un `mouseleave`.
- ⚠️ **Elle DOIT figurer dans la règle `z-index: 10`** aux côtés de `:hover` / `:focus-visible` / `--cover-revealed` — c'est le seul état qui couvre le **retour**. Sans elle le livre retombe à `z-index: 2` **dès le premier pixel du retour** (les deux autres sélecteurs cessent de matcher ensemble, au `mouseleave`) alors que sa couverture fait encore ~300 px de large et pivote : elle est aussitôt peinte **derrière tous les frères qui la suivent dans le DOM**. Seule la part qui recouvre les frères *précédents* reste visible → **une couverture qui semble écrasée/étirée vers la gauche, coincée entre les dos voisins**. C'est le symptôme signalé le 2026-07-28 ; défaut ancien, indolore tant que le retour durait 0,3s. Mesuré (retour gelé image par image, ordre de peinture comparé sur les frères qui recouvrent la couverture, 11 images × 4 livres extrêmes) : **0 recouvrement après correctif, 2 à 39 avant à 390px et 4 à 65 à 1400px** — donc l'ordinateur était touché autant que le mobile.
- Le délai de `visibility` de `.pf-book-cover` (rest, `0s 0.5s`) **doit couvrir toute la durée du retour** : il valait 0,45s, dimensionné pour l'ancien retour de 0,3s.
- ⚠️ **Ne pas diagnostiquer un recouvrement avec `elementFromPoint`** : `.pf-book-cover` est `pointer-events: none` hors saisie, la sonde le traverse et rapporte « masqué » même quand il est peint au-dessus. Comparer l'**ordre de peinture** (`z-index`, puis ordre DOM — tous les livres sont `position: relative`).
- **Vérifié** à 390px : gonflement 2,04× → **1,64×**, glissement horizontal 207 → **81px**. S'applique aussi sur ordinateur (le retour y passe de 0,3 à 0,5s) — choix assumé, l'aller et le retour devenant un seul geste. Invariant d'atterrissage intact après correctif (bandeau/épaisseur = `--pf-obl` au dix-millième : 0,2309 à 390px, 0,3249 à 1400px, y compris sur le livre le plus écrêté, `--pf-reveal-scale` 0,602).
- **Préchauffage de la couverture avant le vol — `.pf-book--arming`.** La couverture est `visibility: hidden` tant que le livre est sur le rayon : elle n'a **jamais été peinte**, et sa première rastérisation tombait sur la **première image du vol**. Une transition CSS étant pilotée par l'horloge et non par les images rendues, ce temps n'est jamais rattrapé — l'animation reprend là où le temps est rendu et **escamote son début**. Mesuré (aire repeinte par image, même métrique des deux côtés) : sur iPhone la 1ʳᵉ image du vol repeignait déjà **78 %** de l'aire de la dernière, contre **5 %** en local — le livre démarrait à ~30 % d'ouverture. Coût **fixe**, d'où sa disparition quand on ralentit l'animation. `bookshelf.js` pose la classe dès que la couverture est chargée puis laisse passer **deux images** avant de déclencher la saisie : la rastérisation se paie pendant que rien ne bouge. Coût : ~33 ms de latence après un tap (au survol, l'attente restante l'absorbe).
  - ⚠️ **Cette règle ne doit poser QUE `visibility`.** Une première version y ajoutait `opacity: 0` (ceinture contre un filet d'antialiasing) et `will-change` : les deux **aplatissent** un membre du groupe `preserve-3d`, ce qui change sa composition avec le dos voisin — filet visible de 4 px de large, écart mesuré **jusqu'à 172/255**, dans les deux variantes. `visibility` seule ne touche pas à la scène et la couverture est de toute façon vue par la tranche (`rotateY(90deg)`, largeur projetée nulle) : vérifié **strictement invisible** (images identiques au pixel entre état préchauffé et non préchauffé, à survol égal).
  - ⚠️ **`visibility 0s 0s` obligatoire dans la règle** : la règle de repos porte `visibility 0s var(--pf-release-dur)`, un délai destiné au **retour**. Le style d'arrivée fournissant la transition, ce délai s'appliquait aussi à l'allumage — le préchauffage arrivait une demi-seconde trop tard, donc après le vol (mesuré : couverture encore `hidden` 500 ms après le début du survol).
  - **Vol allongé à 0,8s sous 767px** (`--pf-reveal-dur` / `--pf-release-dur` dans le bloc mobile) : le préchauffage n'ayant pas suffi, on **dilue** ce qui reste du coût fixe — la même perte de ~55 ms fait démarrer le livre à ~30 % d'ouverture sur 0,5s contre ~20 % sur 0,8s. Les deux mesures se cumulent (l'une attaque la cause, l'autre son résidu). ⚠️ **Les deux sens ensemble** : le retour emprunte volontairement la durée et la courbe de l'aller, les désaccorder ferait claquer le repli. Le minuteur JS suit **tout seul** (il lit la variable, plus aucun nombre en dur) — vérifié : classe tenue ~900 ms à 390px contre ~600 ms à 1400px. 1s diluerait davantage, mais une saisie doit rester une réponse au geste, pas une séquence à regarder.
- **Tactile : l'origine d'un clic se date, elle ne se marque pas.** Le 1er tap saisit le livre (navigation annulée), le 2e suit le lien. ⚠️ Cette bascule **ne peut pas** reposer sur un drapeau que le livre poserait lui-même à son `touchstart` : sur les petites cibles, Safari iOS **recale le `click` vers le lien le plus proche** (*tap target adjustment*) alors que le `touchstart`, lui, part sur la cible réelle. Or un dos ne fait que **10 à 30 px de large avec 12 px de gouttière** — un tap tombe très souvent à côté, sur le rayon. Le livre recevait alors un clic sans avoir jamais vu de `touchstart`, son drapeau restait faux, le gestionnaire laissait filer : **la fiche s'ouvrait sans que la couverture ait été dévoilée** (constaté sur iPhone le 2026-07-29 ; jamais reproduit à la souris, où rien ne recale le clic). Remplacé par une **date globale du dernier contact tactile** (`lastTouchAt`, posée dans l'écouteur `touchstart` de `document` qui existait déjà) : tout clic dans les `TOUCH_CLICK_MS` (1 s) est tactile, quel que soit l'élément qui a reçu le tap. **Vérifié** (tap dans la gouttière + clic recalé sur le dos) : clic annulé, saisie déclenchée ; 1er tap sur le dos → annulé ; 2e tap livre dévoilé → navigation ; clic souris sans tap récent → navigation, comportement inchangé.
  - Un tap dans la gouttière **voisine d'un livre ouvert** est absorbé (`return` si le livre est `--releasing`) : le `touchstart` vient de le refermer et le clic nous est recalé dessus — le geste voulait fermer, pas rouvrir. C'est le pendant tactile du `pointer-events: none` ci-dessous.
- **Le repli est ININTERRUPTIBLE** : `pointer-events: none` sur `.pf-book--releasing` (sous `@media (hover: hover)`). Ramener le curseur sur le livre en plein retour déclenchait `onEnter` → `cancelReleasing()` : la classe tombait en vol, le livre rebasculait en 0,3s avec une autre courbe et repartait pour 700 ms de compte à rebours. `pointer-events` est le **seul** levier qui neutralise vraiment le survol (`:hover` suit le test de collision) et il coupe d'un coup la bascule CSS **et** le `mouseenter` — donc aucun garde-fou JS à ajouter, donc aucun risque de désaccord entre l'état du contrôleur et celui du moteur. **N'expose rien** : le livre ne fait ici que la largeur de son dos au repos (il ne recouvre aucun voisin) et la couverture est déjà repassée en `pointer-events: none` au retrait de la classe de saisie. Clavier intact (`:focus-visible` ne passe pas par le pointeur), tactile hors périmètre (pas de survol à neutraliser, et ça n'y coûterait qu'un tap avalé). **Vérifié** (curseur ramené sur le livre en plein vol) : `:hover` reste faux, la couverture continue de se refermer sans à-coup (70 → 33 → 2 px), la classe tombe à l'heure, le survol se réarme et le livre se re-saisit normalement. *Résidu* : si le curseur est sur le livre à l'atterrissage **et strictement immobile**, `:hover` ne se ré-évalue qu'au premier mouvement — auto-cicatrisant, et pratiquement inatteignable (il faut revenir sur la bande de 22 px pendant le vol puis se figer).
- ⚠️ **`perspective` doit valoir `--persp` DÈS LA PREMIÈRE IMAGE du retour, et la règle de relâchement la redéclare pour le garantir.** C'est la vraie cause de la « couverture étirée vers la gauche » (2026-07-29). La formule de caméra n'est exacte que si la perspective en vigueur est bien `--persp` — l'œil y est posé à `-(--persp + --spine-w)`. Si c'est l'autre perspective du cycle, celle de la bascule (`--pf-tip-persp`, 500 px), le cisaillement devient `|œil| × z / (P + z)` au lieu de `z` : **dos fantôme à 254 px au lieu de 22**, qui traîne le livre hors de l'écran à gauche, la couverture gardant sa largeur correcte. Deux failles cumulées, corrigées ensemble : (a) la règle de relâchement était en (0,2,0), **perdante contre `:hover`** (0,3,0) — si l'état de survol tombe une image après le retrait de la classe de saisie par le JS, la bascule regagne et pose 500 px *instantanément* (`perspective 0s 0s`) ; (b) le délai de commutation valait **toute la durée du retour**, donc une perspective erronée au départ le restait jusqu'au bout. La règle est désormais en (0,3,0) placée après `:hover`, redéclare `perspective: var(--persp)` et commute **sans délai** (dans le cas nominal la valeur ne change pas, il n'y a donc aucune transition à jouer). Le délai de 0,3 s de la règle de base est conservé : il sert au retour de la **bascule**, où la perspective doit rester rapprochée jusqu'au redressement.
  - **Reproduit puis éliminé** (même sonde, survol maintenu pendant le retrait de la classe = pire cas d'ordonnancement) : avant, perspective bloquée à **500 px sur 38 images sur 38**, dos fantôme 254 px décroissant jusqu'à ~35 px en ~240 ms ; après, **0 image hors 6000 px**, dos fantôme ≤ 35 px. Signature optique confirmée en forçant `P = 1200px` avec la caméra calculée sur 6000 : dos fantôme 108 px, couverture intacte à 205,7 px — image superposable à la vidéo fournie.
  - ⚠️ **Pourquoi ça ne se voit pas au ralenti** (piste donnée par l'utilisateur, décisive) : l'artefact **décroît de lui-même** à mesure que la caméra se rapproche (le cisaillement est proportionnel à `|œil|`), donc il occupe les ~170 premières ms quelle que soit la durée. À 0,5 s c'est un tiers de l'animation ; à 15 s, 1 %. Un défaut qui disparaît quand on ralentit est **à durée fixe**, jamais géométrique.
  - ⚠️ **Une mesure « gelée » ne peut pas le voir** : forcer toutes les transitions au même `currentTime` reconstruit un état cohérent par construction. Il faut filmer le compositeur (`Page.startScreencast`) ou relever `getComputedStyle().perspective` image par image en temps réel.
- **Résidu assumé** : la caméra étant interpolée en même temps que la rotation, le bord libre de la couverture passe en cours de vol jusqu'à **29 px à gauche** de sa position finale avant d'y revenir (mesuré sur le livre le plus décalé, `--reveal-dx` −233 px). C'est **géométrique et symétrique** — l'aller traverse exactement les mêmes états, mesurés identiques image par image — donc non corrigeable par un changement de courbe ou de durée. Invisible une fois l'ordre de peinture rétabli.

**Chevalet de prix centré entre le pied du livre et le devant de planche**

Posé sur `bottom: 0`, il ne restait qu'un cheveu entre le livre et le prix (1px à 390px, 6px sur ordinateur) alors que le bois continuait dessous. Il vise désormais le milieu de la bande `réserve + 3px + 0.1 × --plank-h` (`top` + `translate(-50%, -50%)`, avec `bottom: auto` explicite — sinon la boîte serait étirée entre les deux). Vérifié : **4px de chaque côté à 390px, 8/8 à 1400px**.

**Hero de fiche livre — le livre épouse la largeur en mode empilé**

Sous 1024px, `heroFit()` ne faisait que **rétrécir** : le livre restait à sa taille naturelle (172px de large pour 302 disponibles) et réduire le padding ne faisait que resserrer le cadre autour de lui. Il épouse désormais la largeur disponible **dans les deux sens**, comme la branche deux colonnes épouse la hauteur. Padding latéral du hero réduit à 20px sous 767px (`book-single.css`). Vérifié à 390px : livre **172 → 300px de large (+74 %)**, étagère exactement à la largeur du hero (0 débordement — la bordure du cadre est déduite) ; garde-fou à 70 % de la hauteur du viewport pour un livre très élancé ; ≥768px inchangé.

**Caméra du vol repliée dans la `transform` — `--pf-cam-x` / `--pf-cam-y`** (2026-07-29)

L'animation tremblait sur mobile : `perspective-origin` est la **seule propriété du vol que le compositeur ne sait pas jouer**. Elle n'avançait qu'aux recalculs de style du fil principal pendant que la `transform`, elle, était interpolée par le compositeur — chaque image affichée mariait une rotation et une caméra issues de **deux horloges**, et la géométrie avançait par pas inégaux (un fort, un faible, en alternance). Mesuré sur trois vidéos iPhone : **81 à 92 % des images en alternance, 8 à 30 % d'écart** à la moyenne de leurs voisines ; tremblement disparu dès qu'on cessait d'animer la caméra (test confirmé par l'utilisateur).

- **L'équivalence exacte** : déplacer l'origine de perspective de `(a0,b0)` vers `(a,b)` revient à prépendre à la transform un **cisaillement en z** — `x' = x − (a−a0)/P·z`, `y' = y − (b−b0)/P·z`. Le terme de translation se simplifie, et ce cisaillement **commute avec les translations en x/y**, donc `transform-origin` ne s'en mêle pas : on peut le mettre en tête de liste sans rien d'autre à ajuster. Au repos et pendant la bascule il est l'identité.
- `perspective-origin: 50% 0%` devient **fixe et n'est plus jamais animée** : c'est le **repère `(a0,b0)`**, que `computeRevealShift()` **lit sur l'élément** au lieu de le recalculer — unique source. `perspective` continue de commuter instantanément comme avant.
- ⚠️ **La formule vit désormais en JS et ne peut pas revenir en CSS** : les coefficients sont **sans unité** et CSS ne sait pas diviser une longueur par une longueur. `computeRevealShift()` publie `--pf-cam-x` / `--pf-cam-y`, le CSS les place dans un `matrix3d(1,0,0,0, 0,1,0,0, x,y,1,0, 0,0,0,1)` en tête des listes de bascule et de saisie (listes toujours alignées, cf. l'avertissement sur l'interpolation).
- ⚠️ **`--reveal-dx` est arrondi AVANT usage** : le CSS reçoit la valeur arrondie, la caméra doit être calculée sur exactement la même.
- **Vérifié** : **768 valeurs de géométrie** (4 livres × 2 largeurs × 8 avancements × 3 faces × 4 coordonnées), **écart maximal 0,00 px** avec l'ancienne formulation — l'atterrissage *et* tout le trajet sont identiques. Après repli, plus aucune animation de `perspective-origin` ; il ne reste hors compositeur que les largeurs de bordure des plats (`.pf-book-pages`, 1,5 px sur toute la durée) — candidat suivant si un résidu subsistait.

**Projection — les deux modes partagent une seule caméra (`--pf-obl`)**

Le mode **covers** est une projection **cavalière** : reculer d'une profondeur `d` décale de `(-d, -[--pf-obl]·d)` à l'écran. D'où le `skewY(18deg)` du dos et le parallélogramme du bandeau de pages (`tan 18° = 0,3249` ; `13°`/`0,2309` sous 768px). Anatomie 2D pure, aucun coût 3D — important, le catalogue en affiche ~300.

⚠️ `--pf-obl` et le `skewY` sont **la même grandeur écrite deux fois** (l'un est la tangente de l'autre) : les changer ensemble, aux deux points de rupture. L'angle est passé de 14°/10° à 18°/13° le 2026-07-25 — vue légèrement plus haute, donc bandeau de pages ~30 % plus épais, ce qui laisse la place au plat arrière (ci-dessous) sur les livres minces. Marge disponible vérifiée : `.pf-shelf-books` a 40 px de `padding-top` et le bandeau du livre le plus épais du catalogue (dos 41 px) en occupe 13,3.

Le mode **spines** est un vrai volume 3D (dos, couverture, face supérieure = les faces d'un même solide, `.pf-book-inner` en `preserve-3d`). La face supérieure `.pf-book-pages` est un plan horizontal (`rotateX(-90deg)`) : elle suit donc la rotation **par construction**, il n'y a rien à resynchroniser.

Le raccord entre les deux se fait par une **caméra mobile** (`perspective-origin` animée sur `.pf-book`, en phase avec la rotation) :
- **au repos** : `50% 0%` — l'œil est pile à hauteur du dessus du livre, la face supérieure est rasante donc invisible ; l'étagère au repos est strictement inchangée ;
- **livre posé** : l'œil monte et se décale à gauche jusqu'à `calc(--reveal-dx - (--persp + --spine-w))`, `calc(--reveal-dy - 0.1·--book-h - --pf-obl·(--persp + --spine-w))`.

Cette formule est **exacte, pas approchée** : un point à la profondeur `p` se projette avec le décalage `(px - x0)·p/(persp + p)` ; en posant `px = x0 - (persp + --spine-w)`, le décalage à `p = --spine-w` vaut exactement `-(--spine-w)`. Le livre posé retrouve donc exactement la **construction** d'un livre covers — même angle de fuite, même rapport bandeau/épaisseur (vérifié : 0,325 des deux côtés pour un `--pf-obl` de 0,3249, et 0,176 sous 768px avec l'ancienne valeur). ⚠️ **Construction, pas superposition** : les deux rendus n'ont ni la même taille ni le même habillage, cf. « Ce que les deux modes ne partagent pas » plus bas. Les termes `--reveal-dx`/`--reveal-dy` (recentrage JS) et `-0,1·--book-h` (le `scale(1.1)`, d'origine `left bottom`, remonte le haut du livre) repèrent le coin haut-gauche du volume posé — sans eux le bandeau perd ~10 % d'épaisseur.

**Ce que les deux modes ne partagent pas** (mesuré sur un même livre, le 2026-07-27)

Un livre saisi en spines n'est **pas** un livre covers au repos : seule la *construction* est commune. Écarts, du plus structurant au plus anecdotique :

| | covers (repos) | spines (dévoilé) |
|---|---|---|
| `--book-h` / `--cover-w` / `--spine-w` | 286 / 190 / 41 | 428 / 284 / 61 |
| couverture rendue | 190 × 286 | 312 × 471 |
| bandeau de pages | 13,31 px | 19,82 px |
| **bandeau / épaisseur** | **0,325** | **0,325** |
| dos : arête arrière / arête avant | 1,000 | 0,952 |
| image servie | `pf-shelf-cover` (398×600) | `medium_large` (768×1157) |
| ombre de volume (`.pf-book-inner`) | `-11px -11px 8px` | aucune |
| ombre du dos | `-1px 0 3px` | `inset -2px 0 4px` + `1px 1px 4px` |
| fond de `.pf-book-inside` | crème `--pf-cream-dark` | blanc |

- **Facteur 1,65 en taille** = `mode_scale` **1,5** (le mode spines dessine tout plus grand pour que les titres verticaux des dos restent lisibles, cf. `prepare_books()`) × **1,1** (le `scale` de la saisie). C'est de loin l'écart dominant, et il est **voulu** : les deux modes ne servent pas le même usage.
- **La couverture est donc servie en `medium_large`** en spines (et non en `pf-shelf-cover`), sinon l'agrandissement serait flou — sans coût, l'image n'étant chargée qu'au survol réel.
- **Seule la ligne en gras est un invariant** : le rapport bandeau/épaisseur vaut `--pf-obl` dans les deux modes, c'est ce que la caméra mobile garantit. Tout le reste diverge.
- **La projection, elle, n'est pas du même type** : covers est parallèle (cavalière → arêtes du dos strictement parallèles, pentes **-0,3249 en haut ET en bas**), spines est une vraie perspective (fuite derrière). D'où un **écart de pente haut/bas du dos** propre à spines, réglé par `--persp` : 0,3725 à 1200px — l'arête basse filait deux fois plus raide que la haute, visible à l'œil —, 0,1534 à 3000, **0,0775 à 6000 (valeur retenue le 2026-07-27)**, 0,0389 à 12000. L'arête HAUTE, elle, vaut `--pf-obl` quelle que soit la valeur : la formule de caméra la fixe (terme `-0,1·--book-h`), pas l'arête basse.
  - **`--persp` n'a aucun effet sur l'atterrissage** (les termes `--persp + --spine-w` s'annulent) : épaisseur du bandeau 19,82 px et largeur de dos projetée ~60 px identiques de 1200 à 40000, et étagère au repos **pixel pour pixel identique** (0 pixel d'écart). Il ne coûte que la profondeur ressentie pendant les ~150 premières ms de la saisie (rapprochement des bords de la couverture en rotation : 0,876 à 1200px → 0,973 à 6000) ; au-delà l'easing a fini de tourner le livre.
  - ⚠️ **On ne peut pas atteindre le parallèle exact en spines** : `perspective: none` ne rendrait pas la projection cavalière, il ferait *disparaître* le bandeau de pages — la face supérieure est un plan horizontal qui n'existe à l'écran que par la perspective. On ne peut que s'en approcher en éloignant l'œil.
- Les trois écarts d'habillage (ombre de volume, ombre du dos, fond intérieur) sont des **oublis**, pas des décisions : les règles correspondantes ont été écrites scopées `--covers` ou `--spines` sans que l'autre mode soit repassé dessus. Sans conséquence tant qu'on ne compare pas les deux côte à côte.

⚠️ **Ne pas réintroduire de « déco » plate.** Une réplique 2D de l'anatomie covers (`.pf-book-held-deco` / `.pf-spine-ghost` / `.pf-pages-ghost`, supprimée) ne peut pas suivre la perspective en vol : l'arête haute du volume plonge jusqu'à ~45 px sous un bandeau plat pour un livre de 306 px. Écart mesuré pendant le vol : **1,4 px** (antialiasing) avec le volume 3D, contre 7 à 25 px avec la déco plate. La suppression retire aussi 3 nœuds DOM par livre (10 → 7) et l'animation de `clip-path` : **0 layout par cycle contre 6**, à 60 fps dans les deux cas.

⚠️ En mode spines, `.pf-book-inside` ne doit **pas** être reculé en profondeur pour éviter le z-fighting (l'ancien `translateZ(-1.5px)`) : l'œil étant déporté à gauche, ce retrait se projette latéralement et laisse un liseré blanc le long du dos. Arbitrer par `z-index` (cover 2 / inside 1).

⚠️ **L'ouverture de couverture au curseur ne peut pas vivre dans l'espace 3D du volume.** La caméra y étant déportée de ~45°, la profondeur prise par la couverture qui bascule se traduit en décalage latéral : mesuré **+53 % de largeur à −25°**, la couverture s'étirait vers la droite au lieu de pivoter. D'où `.pf-cover-leaf` (émis par le PHP en spines non-héros non-liseuse) : `.pf-book-cover` reste la face rigide du volume et devient l'hôte d'une **scène 3D locale** (`perspective` propre + `transform-style` plat par défaut → le pivot est aplati dans le plan de la face avant que la caméra du volume n'intervienne). Perspective proportionnelle (`calc(var(--cover-w-base) * 5.2)`, ratio repris du 1500/288 de covers) plutôt que 1500px fixe, le livre saisi étant rendu plus grand qu'en covers. Vérifié : largeur à −25° = **0,942×** contre **0,943×** en mode covers.

**Survol en mode spines — la bascule (étape 1, avant la saisie)**

Au survol, le livre **bascule vers le lecteur autour de son arête basse** (`rotateX` de `--pf-tip`, 10°, origine `left bottom` déjà en place) : le pied ne bouge pas, le haut du dos vient vers l'avant. Remplace l'ancien `translateZ(16px)`, qui ne faisait qu'agrandir uniformément et ne dévoilait rien. **Aucun agrandissement** : le geste seul détache le livre du rang.

- **La face supérieure entre dans le champ sans rien ajouter** : rasante au repos (la caméra est pile à sa hauteur, `perspective-origin: 50% 0%`), il suffit de l'incliner. Elle s'ouvre **verticalement au-dessus du dos**, sur toute sa largeur — et non en fuyant vers le haut-gauche comme à la saisie, puisqu'il n'y a pas de rotation autour de l'axe vertical ici.
- **Hauteur du bandeau = profondeur du livre × sin(`--pf-tip`)**, donc proportionnelle à la profondeur (un livre plus profond montre plus de dessus, c'est juste). Mesuré à 10° : **48 px** pour un livre courant (284 px de profondeur), **101 px** pour la fiche à 178,5 cm (saisie erronée, écrêtée à 350 mm — **à corriger côté données**).
- ⚠️ **Aucun recentrage vertical, volontairement** (décision du 2026-07-27) : la bande dépasse les 40 px de dégagement de `.pf-shelf-books` et le scroller la rogne. Assumé — 1,4 px coupés sur un livre courant, davantage sur un grand format. **Ne pas réintroduire de nudge ici** : à cet angle il faudrait redescendre presque tous les livres et le survol deviendrait un saut, pour un bandeau que le lecteur voit de toute façon apparaître. La saisie garde le sien (`computeRevealShift`), où l'enjeu est la couverture entière.
- **Perspective PROPRE à la bascule** (`--pf-tip-persp`, 1200px, posée sur `:hover`/`:focus-visible`) : un livre qu'on incline vers soi doit **s'évaser**, le haut se rapprochant. Avec `--persp` (6000px, réglé pour les arêtes parallèles du livre *saisi*), l'évasement tombait à **1,18 %** — 0,7 px sur un dos de 60, invisible : il ne restait que le raccourcissement de 1,5 % et le geste se lisait comme une translation. Mesuré à 10° : 6000px → 1,18 %, 2000px → 3,85 %, **1200px → 6,59 %**. 1200px est la valeur physique (incliner de 10° un livre de 21 cm vu à ~55 cm rapproche son haut de 3,6 cm, soit 6,5 % de grossissement) — et c'était la valeur d'origine du fichier.
  - ⚠️ **`perspective` n'est JAMAIS interpolée dans le cycle de survol**, elle est commutée à un instant où elle ne se voit pas — livre à plat, où tout est à z = 0 et le facteur de projection vaut 1 quelle que soit la valeur (0 pixel d'écart au repos entre 600 et 6000px). Interpolée, elle **arrive en retard sur son effet** : celui-ci varie en 1/(P−z), donc l'essentiel se joue en fin de course — de 6000 à 600px, à mi-transition on n'a que ~16 % de l'évasement final, d'où l'impression qu'elle s'applique *à la fin* de la bascule. D'où : **aller** `perspective 0s 0s` dans la règle `:hover` (posée avant que le livre ne bouge — la redéclarer là est OBLIGATOIRE, sinon la règle de repos s'applique avec son délai) ; **retour** `perspective 0s 0.3s` dans la règle de repos (elle ne revient qu'une fois le livre redressé). Vérifié image par image : perspective à 600px dès la 1ʳᵉ frame, évasement 0 → 14,1 % sur les 300 ms de rotation ; au retour elle reste à 600px pendant tout le redressement et ne bascule à 6000 qu'une fois l'évasement revenu à 0.
  - **Les deux états ne sont pas la même situation de vision** — livre posé sur le rayon qui se penche vers vous / livre tenu de face — donc pas la même distance d'œil. La saisie **rétablit `--persp`** (son `perspective-origin` est calculé dessus).
  - ⚠️ **`perspective` ne s'interpole nulle part — les trois commutations sont instantanées**, chacune placée là où elle ne se voit pas : à l'aller livre à plat (facteur de projection 1 quelle que soit la valeur), au retour une fois le livre redressé (délai 0.3s), **et au départ du vol**. Ce dernier point est le correctif du 2026-07-28 : interpolée pendant le vol, elle le rendait **non monotone** — avec l'œil rapproché, la couverture qui recule jusqu'à ~280 px de profondeur est projetée si violemment qu'elle s'ouvrait, se refermait, puis se rouvrait. Saut maximal par image sur la boîte du volume : œil de bascule tenu pendant le vol **26,3 px** (3 retours en arrière), interpolé 500→6000 **26,3 px** (3 retours), **rendu d'un coup 7,1 px (0 retour)**, référence sans bascule rapprochée 7,0 px. La commutation tombe pile quand la rotation démarre et son saut (6,4 px sur la 1re image) est du même ordre que le déplacement normal entre deux images (6,1 px) : invisible. Vérifié : bascule à 1200px et 6,59 % d'évasement, atterrissage inchangé (bandeau 19,82 px, dos projeté 60 px, pentes -0,3249 / -0,4024 comme avant), repos **pixel pour pixel identique**.
- **Plats amincis pendant la bascule** (`--pf-backcover-tip`, 2,5px contre 4px) : `--pf-backcover` est une exagération calibrée pour les vues **comprimées** — bandeau covers, livre saisi — où elle se projette sur ~1px, au vrai ratio (0,3 mm) le carton y serait invisible. La bascule, elle, montre la face supérieure **quasi de face, sans compression** : la même valeur y occupe 13 % de l'épaisseur du livre et les couvertures paraissent épaisses. L'exagération doit donc suivre la compression de la vue. **La position saisie n'y touche pas** : elle rétablit `--pf-backcover`, sur la durée du vol (1,5px de chaque côté, invisible à ce rythme — mais un saut se verrait, la face supérieure étant encore vue de face au départ). ⚠️ Chrome rabote la largeur de bordure au pixel-appareil : 2,5px rend **2px** en dsf 1, 2,5px en dsf 2.
- **Ombrage de BASCULE du bloc de pages** (`.pf-book-pages::after`) : **même cycle de vie que l'ombre de bascule du dos** — il monte avec la bascule et s'éteint à la saisie (le livre y est tenu de face, plus penché). Vérifié image par image : les deux opacités suivent exactement la même courbe, 0 → 1 sur les 300 ms de rotation, retour à 0 au redressement, et 0 dans l'état saisi. ⚠️ Porté par un **pseudo-élément en opacité**, plus par une couche de `background` : un dégradé ne s'interpole pas, il serait apparu d'un bloc. Son `inset: 0` se cale sur la boîte de padding → l'ombre couvre le papier sans mordre sur les deux plats, qui gardent leur teinte. Désactivé sur le boîtier CD, qui porte déjà son propre ombrage plastique en sens inverse. Écart assumé avec le mode covers, dont le bandeau garde un ombrage permanent (il y est toujours visible).
- **Ombre de bascule** (`.pf-book-spine::after`, dégradé nul en haut → `rgba(0,0,0,.3)` en bas, opacité 0→1 au survol) : le pied reste au fond du rayon quand le haut vient au lecteur, c'est donc lui qui garde l'ombre. Sans elle la rotation ne se lit qu'à l'apparition du bandeau ; avec, le dos lui-même raconte le geste. `::after` car `::before` porte déjà le voile de saisie (le flanc assombri) — les deux coexistent, l'`::after` passe au-dessus par ordre du DOM à `z-index` égal. Éteinte dès la saisie, où le voile prend le relais.
- **Plat AVANT ajouté à droite du bandeau** (`border-right`, même carton que le plat arrière) : vue quasi de face, la face supérieure se lit **[plat | pages | plat]**, ce qui la ferme même quand la couverture n'est pas encore chargée (elle ne se télécharge qu'après 400 ms de survol). **Retiré dès que la saisie commence** — le livre y montre sa vraie couverture et ce trait ferait doublon avec son bord haut. Retiré en `border-right-color: transparent`, **jamais en `width: 0`** : la largeur entre dans le border-box, la remettre à zéro élargirait le bloc de pages de 4 px en pleine animation.
- ⚠️ **Les listes de fonctions de `transform` des étapes 1 et 2 sont ALIGNÉES** (mêmes fonctions, même ordre, valeurs neutres à l'étape 1 — vérifié à la lecture du CSSOM : `translateX > translateY > scale > translateZ > rotateY > rotateX` des deux côtés). Sans ça le navigateur interpole par décomposition de matrice et le vol prend une trajectoire parasite. Les deux règles ont la **même spécificité** : c'est l'ordre dans le fichier qui fait gagner l'étape 2 — ne pas la remonter.
- **Non-régression** : étagère au repos **pixel pour pixel identique** (0 pixel d'écart > 3/255). La liseuse bascule sans bandeau (le PHP ne lui en émet pas — un appareil n'a pas de bloc pages) ; le boîtier CD garde son plastique sombre sur les deux bords.
- ⚠️ **Piège de test** : un `mouseenter` synthétique en JS ne fait **pas** matcher `:hover` en CSS — la bascule reste invisible et on conclut à tort qu'elle ne marche pas. Seul un vrai déplacement de pointeur (`Input.dispatchMouseEvent`, type `mouseMoved`) met à jour l'état de survol du moteur de rendu. La saisie, elle, est pilotée par une classe, donc insensible à ce piège.

**Assombrissement de profondeur — une seule règle pour les deux modes** (2026-07-28)

Toutes les faces qui fuient vers l'arrière s'assombrissent **progressivement vers le fond**, jamais d'un voile uniforme : `linear-gradient(… 0 → rgba(0,0,0,.18))` orienté selon l'axe de profondeur de la face. Le bandeau de pages du mode covers le faisait depuis toujours ; le **dos** ne recevait qu'un voile plat à `0.1`, qui l'aplatissait. Même amplitude que le bandeau (0.18), donc **même moyenne (0.09) que l'ancien voile** : c'est la répartition qui change, pas la quantité d'ombre.

| face | où | axe |
|---|---|---|
| bandeau de pages | covers, en permanence | `to bottom` (haut = fond) — inchangé |
| dos | covers, en permanence | `to left` (gauche = fond) |
| dos | spines, livre saisi (`::before`) | `to left` |
| bandeau de pages | spines, livre saisi (`::before`) | `to left` |

- ⚠️ **L'axe de profondeur du bandeau CHANGE entre les deux états de spines**, d'où deux pseudo-éléments et non un seul : livre basculé on regarde le dessus depuis l'avant, le fond est la gouttière (axe local **y**, `::after`) ; livre saisi la caméra est partie à gauche, le fond devient le plat arrière (axe local **x**, `::before`). Un `background` ne s'interpole pas → les deux couches se croisent en opacité pendant le vol.
- **Le dos, lui, garde le même axe dans les deux modes** : son arête gauche est la plus lointaine des deux côtés (en spines saisi elle se projette à `z = -1.1 × --spine-w`), d'où un dégradé identique.
- Vérifié au pixel sur le bandeau saisi : haut (fond) `rgb(196,191,177)` → bas (avant) `rgb(209,201,183)`, soit le même sens qu'en covers ; avant le correctif le bandeau saisi n'avait **aucun** ombrage.

**Quatrième de couverture — le plat arrière peint sur l'arête du fond du bandeau**

Le bandeau de pages ne montrait que du papier : le bloc semblait flotter sans reliure. On y peint donc le **plat arrière**, à la couleur dominante de la couverture (la même que celle des dos générés, `--cover-color` posée en inline sur chaque `.pf-book`), assombrie de 15 % — le carton est dans l'ombre du livre. C'est une **bordure de `.pf-book-pages`**, donc immobile par rapport au bandeau et sans nœud DOM supplémentaire.

- **Même arête physique dans les deux modes, deux côtés différents.** En covers le bandeau est un parallélogramme 2D et le fond du livre est son **arête haute** → `border-top`, du coin haut-gauche du dos au coin haut-droit du bandeau, parallèle au bord haut de la couverture. En spines c'est un plan couché dans l'espace, dont la largeur locale est l'épaisseur du livre (la couverture est charnée à droite, en `x = --spine-w`) → le fond est à **gauche**, `border-left`. Une fois le livre saisi et la caméra en place, ce bord se projette exactement là où tombe le `border-top` de covers.
- **D'où deux écritures de la même épaisseur** : `calc(var(--pf-backcover) * var(--pf-obl))` en covers (une profondeur projetée) contre `var(--pf-backcover)` brut en spines (une profondeur dans le plan).
- **`box-sizing: border-box` obligatoire** : le carton fait partie de l'épaisseur du livre, il ne s'y ajoute pas. Sans lui le bandeau grossirait de la valeur du plat.
- **`--pf-backcover: 4px`** = 3,3 mm à l'échelle du site, soit un carton de reliure plutôt qu'une couverture souple. Exagération assumée : au vrai ratio (0,3 mm) le plat se projetterait sur 0,1 px. Une **profondeur constante** (et non un pourcentage du dos) est le bon modèle — un carton ne s'épaissit pas avec le nombre de pages —, et la projection étant linéaire elle donne bien un trait d'épaisseur constante. À l'écran : **1 px** partout (Chrome rabote la largeur de bordure au pixel-appareil, et la **relève à 1 px minimum** — vérifié à 768px où la valeur calculée tombe à 0,92 px, donc le trait ne disparaît jamais).
- ⚠️ **`--pf-backcover-ink` est déclarée sur `.pf-book-pages`, pas sur `.pf-bookshelf`** : la valeur d'une custom property est substituée sur l'élément où elle est **déclarée**. Écrite sur le conteneur, le `var(--cover-color)` imbriqué se résoudrait contre le conteneur — qui ne la porte pas — et jamais contre le livre.
- **Dos à angles vifs, bandeau calé dessus au pixel** (2026-07-25) : les `border-radius` des dos ont été retirés — `2px 0 0 2px` en covers, `2px` en spines (la liseuse garde ses 4px, c'est un appareil, pas un livre). En conséquence `.pf-book-pages` épouse désormais **exactement** le livre (`left: 0`, largeur `--cover-w + --spine-w`) : les quatre sommets du `clip-path` tombent sur des points réels du volume. La boîte était auparavant rentrée de 1px à gauche pour se cacher derrière l'arrondi ; sans arrondi, ce décalage laissait un **liseré blanc diagonal d'1px sur toute l'arête haute du dos** (vu au zoom 24×, corrigé). Vérifié sur les 165 livres, aux deux points de rupture : écart nul entre le bord gauche du bandeau et celui du dos, entre son extrémité droite et le bord de la couverture, et entre son bas et le haut de la couverture.
- **Boîtier CD** : `border-color` ramené au plastique sombre — le dos d'un boîtier cristal n'est pas un plat cartonné.
- **Livres très minces** : le catalogue descend à un dos de 4 px (bandeau de 1,3 px), où le trait de 1 px occupe l'essentiel du bandeau. Laissé tel quel : à cette taille le bandeau est déjà un cheveu, et un opuscule de 3 mm est effectivement surtout de la couverture. Plafonner le plat à un pourcentage du dos ne changerait rien à l'écran (la bordure retomberait sur le même pixel unique).
- **Non-régression** : étagère spines **au repos** pixel pour pixel identique (0 pixel d'écart > 3/255) — au repos la caméra est rasante, la face supérieure reste invisible.

**Dos fictifs (pas d'image de `tranche`) — couleur, encre, logo, titre**

> ⚠️ Vocabulaire : le champ SCF s'appelle `tranche` mais désigne le **dos**. La vraie tranche (de tête) est la face supérieure, `.pf-book-pages`.

- **Couleur = dominante de la couverture**, calculée par `dominant_color()` : réduction en 64×64 puis **histogramme quantifié** sur 4 bits/canal (4096 casiers — sans quantification deux pixels n'ont presque jamais la même valeur et le comptage ne veut rien dire). Casier gagnant = max de `fréquence × (0,25 + saturation)`, en écartant les casiers quasi blancs (papier, L > 0,93) et quasi noirs (encre, L < 0,07). Repli en cascade sur `PASSIFLORE_RED`.
  - **Pourquoi pas la moyenne** (ancien resize 1×1) : elle régresse vers un gris-brun dès que la couverture est contrastée → **39 %** des dos avaient un titre blanc illisible. **Pourquoi pas un pixel du coin ni la moyenne du bord** : c'est souvent le blanc de la marge → 5 à 6 dos quasi blancs sur 33 (testé).
- **Extraite pour TOUTES les couvertures**, pas seulement les livres sans image de dos : le plat arrière du bandeau de pages (ci-dessous) en a besoin, et ce bandeau existe quel que soit le dos. Seule exception, les liseuses (pas de bloc pages, pas de couverture cartonnée). 165 couvertures distinctes sur ce catalogue contre 33 dos générés.
- **Cache** : post-meta `_pf_cover_color` sur la **pièce jointe** (donc mutualisée entre éditions partageant une couverture), calculée une seule fois à vie. **Changer l'algorithme = incrémenter `COLOR_ALGO_VER`** : `maybe_purge_cover_colors()` (hook `admin_init`, option `pf_cover_color_algo`) purge alors la meta une fois par environnement, cache objet compris. Rien à lancer à la main au déploiement — idiome maison, cf. `pf_auteur_terms_synced`.
  - **Préchauffage par lots** (`maybe_warm_cover_colors()`, `admin_init` prio 11, option `pf_cover_color_warm`, `COLOR_WARM_BATCH = 15`) : l'extraction coûte **~30 ms par couverture** (mesuré), soit **~3,8 s en local** si le premier rendu du catalogue devait les calculer toutes d'un bloc — et l'hébergement de prod est nettement plus lent. On draine donc 15 images par écran d'admin jusqu'à épuisement, puis l'option coupe court (une seule lecture ensuite). Le rendu reste capable de calculer à la volée : c'est une avance de phase, jamais une dépendance. La purge de version efface aussi ce drapeau.
- **Encre selon le fond, pas de correction de la couleur** : `spine_is_light()` teste le contraste WCAG du **blanc** sur le fond ; sous 4,5:1 le dos reçoit `.pf-spine-generated--light` → titre et logo en `--pf-heading`, ombre portée inversée. On garde la couleur exacte de la couverture (un livre pâle a un dos pâle, comme en vrai) plutôt que de l'assombrir pour sauver le texte blanc.
- **Logo** : c'est **le même macaron dans les deux cas**, seul le coloris change. Dos sombre → `assets/img/macaron_logo_blanc-96.png` (version blanche ; l'original fait 520 px pour un affichage à 24 px, d'où la copie 96 px générée — ce n'est **pas** un média WordPress, donc aucune sous-taille automatique, il faut la régénérer à la main si l'original change). Dos clair → site icon (rayons noirs + fleur rouge). Les deux sont **détourés** (fond transparent) ; le `img.pf-spine-icon { border-radius: 50% }` est donc sans effet visible, hérité d'un éventuel site icon carré.
  - ⚠️ Piège d'analyse : ouvrir ces PNG avec `PIL.Image.convert('RGB')` composite la transparence sur du **noir** et donne l'illusion d'un carré noir opaque. Vérifier le canal alpha (`im.mode`, coins) avant de conclure quoi que ce soit sur ces images.
- **Titre** (`spine_title_html()`) : le **suffixe entre parenthèses est retiré**. Sur ce catalogue il vaut toujours `(grands caractères)`, `(numérique)` ou `(deuxième édition)` — un marqueur de format, jamais du titre, et qu'aucun imprimeur ne mettrait sur un dos. C'était aussi la cause des débordements : les 3 seuls titres dépassant 42 caractères le devaient entièrement à ce suffixe.
- **Composition : auteurs en haut, titre au milieu, logo en bas** — trois enfants flex en `space-between`, donc le titre se centre tout seul. L'élément `.pf-spine-authors` est **émis même vide** pour que ce centrage tienne aussi sur les livres sans auteur. Les liseuses n'ont pas d'auteurs (un chant d'appareil n'est pas un dos de livre).
- **Auteurs** (`spine_meta_for()`) : **toutes** les contributions, dans l'ordre du repeater SCF, via `passiflore_get_product_author_ids()`. Format « A & B », « A, B & C ». Patronyme et prénom viennent des term meta `nom` / `prenom` de la fiche auteur (pas d'un découpage du nom du terme, qui casserait sur « Le Déodic » ou « Saüquère-Hubert »).
  - **Le prénom n'est conservé que pour un auteur SEUL.** À partir de deux, on passe directement aux patronymes : mesuré sur le catalogue, la forme complète fait 30 à 52 caractères contre 15 à 28 pour les patronymes — toujours au moins le double, et souvent plus longue que le titre lui-même (« Ironda à colorier » : 17 caractères de titre pour 30 d'auteurs). Les prénoms composés français (« Jean-Michel », « Marie-Laure ») y sont pour beaucoup. C'est aussi l'usage typographique sur un dos à plusieurs auteurs.
- **Polices** (`spine_meta_for()` → classe `.pf-spine-generated--serif`) : titre en **Newsreader 700** (serif) sous « Littérature », en **Inter 700** sous « Culture Sud-Ouest » ; auteurs toujours en **Inter 400**. Résolution **par livre** (on remonte l'arbre `product_cat` jusqu'à la racine), pas par étagère — `resolve_category_theme()` reste, lui, une propriété de l'étagère entière. ⚠️ Kadence ne charge **Newsreader qu'en 700** : ne pas demander d'autre graisse, elle serait synthétisée. Les deux familles sont déjà chargées, rien à ajouter.
- **Amorçage en lot obligatoire** : `spine_meta_for()` fait 1 requête pour l'arbre `product_cat`, 1 pour les catégories des livres, 1 `_prime_term_caches()` pour les termes auteur **et leurs métas**. Sans ça on retomberait sur le N+1 déjà corrigé pour les pièces jointes.
- **Corps du texte** (`spine_layout()`) — contraint par les **deux** dimensions, par pas de 0,5 px :
  - hauteur : hauteur interne (padding 8+6 déduit) **moins la place du logo** moins une respiration, ÷ le coût du texte. Coût = caractères × em/caractère, les auteurs comptant `SPINE_AUTHOR_RATIO` (0,85) de moins. Les em/caractère sont **mesurés au canvas** sur un corpus de vrais titres et noms : Newsreader 700 = 0,480, Inter 700 = 0,513, Inter 400 = 0,497 (constantes `SPINE_EM_*`, letter-spacing 0,02em inclus).
  - largeur : (`spine_w_px` − 4 px de padding) ÷ 1,15 (le `line-height`) — ce qui fait grossir le texte sur les livres épais et le contient sur les minces.
  - **Échelle de repli** quand tout ne rentre pas, le titre étant l'identifiant principal donc toujours protégé : `Prénom Nom` (**auteur seul uniquement**, cf. ci-dessus) → **patronymes** → `Nom & al.` (2 auteurs et plus) → **titre seul**. On descend d'un cran tant que le corps calculé passe sous `SPINE_FONT_OK` (9 px, seuil de *confort*) ; `SPINE_FONT_MIN` (7) n'est que le plancher absolu. Sur un dos très mince c'est la largeur qui plafonne et aucune forme d'auteur n'y changerait rien → pas de dégradation dans ce cas. Filet ultime : `overflow:hidden` + `text-overflow:ellipsis`, et le logo est `flex-shrink: 0` donc jamais chassé.
  - Simple arithmétique, donc calculé au rendu **sans cache** (contrairement à la couleur, qui fait du traitement d'image). Vérifié sur les 33 dos générés : 27 avec auteurs, 20 serif / 13 sans, **0 débordement, 0 troncature, logo jamais écrasé**.

**Chargement des couvertures — `decode()` obligatoire** (`bookshelf.js`, `startCoverLoad`). L'événement `load` ne signifie que « octets reçus » : le décodage en bitmap arrive plus tard, à la première peinture qui en a besoin — c'est-à-dire pile sur la première image de la rotation, d'où une saccade au tout **premier** dévoilement de chaque livre (les suivants sont fluides, l'image étant décodée en cache). Mesuré : 3 à 15 ms après `load` en local, davantage sur machine lente. `img.decode()` force ce travail en amont ; le délai est entièrement absorbé par les `REVEAL_DELAY_MS` (vérifié : rotation toujours déclenchée à ~702 ms après le survol, donc aucune latence ajoutée).

**Mode `scroll` — ombres de bord** (`render_scroll()`, composant global `.pf-scroll-fade`)

Signale les livres hors champ, sur **toute** étagère en mode scroll (accueil ×7, fiche auteur, fiche événement, livres associés) : c'est `render_scroll()` qui pose le composant, donc c'est acquis pour toute étagère scroll à venir. Le mode `shelves` n'en a pas besoin — ses rangées sont re-réparties pour la largeur réelle, rien ne sort du champ. Détail complet : `docs/design-system.md` § B.9.

- **Le wrap s'intercale entre le CADRE et le scroller** (`.pf-bookshelf` → `.pf-scroll-fade` → `.pf-shelf`) : le masque du composant, posé sur `.pf-bookshelf`, aurait dissous avec les livres sa bordure, ses coins arrondis et son ombre portée. `.pf-shelf` étant déjà le scroller, sa boîte est celle du wrap au pixel ; les deux partageant `--wall-color`, seuls les livres et la planche s'effacent.
- ⚠️ **Le wrap doit rester transparent à la mise en page** : l'accueil étire `.pf-shelf` sur la hauteur de son bloc (`.pf-etagere-bloc .pf-bookshelf` en flex column, `.pf-shelf` en `flex:1`) — d'où `.pf-bookshelf--scroll > .pf-scroll-fade` qui relaie la chaîne flex, inerte ailleurs. Géométrie des 7 étagères de l'accueil vérifiée identique au pixel.
- **Rampe réduite avec la fenêtre** (`--pf-fade-size`) : 60px valent 5 % d'un rayon d'ordinateur mais 18 % à 390px → **40px ≤1023px, 28px ≤767px**.
- **Câblage** : `bookshelf.js` rappelle `window.pfScrollFade(document)` en fin d'`init()`, **après `relayoutAll()`** (qui fixe la largeur des livres, donc le `scrollWidth` comparé à la fenêtre) → couvre les étagères injectées par AJAX. Script enregistré par `register_assets()`, enqueué par `render_scroll()`.

**Mode `shelves` — voile jusqu'au re-packing** (`render_shelves()`, `bookshelf.css`, `relayoutAll()`)

Le PHP répartit les livres par rangée pour une étagère de **1100px** (le serveur ignore la largeur du viewport) ; `repackShelves()` re-répartit pour la largeur réelle au `DOMContentLoaded`. Entre les deux, la répartition théorique était **peinte** : les rangées étant en `nowrap` centrées, les livres en trop débordaient à gauche **et** à droite, puis sautaient sur les rangées suivantes. Mesuré au contrôle (catalogue, 700px, voile retiré) : **14 images peintes sur 370 ms, jusqu'à 161 px de débordement**.

- **Voile** : `.pf-bookshelf--shelves.pf-shelves-js:not(.is-packed) { visibility: hidden }`, levé par `relayoutAll()` (classe `.is-packed`) une fois `fitBookshelf` **et** `repackShelves` passés. Posée **inconditionnellement** sur toutes les étagères shelves : `repackShelves` peut sortir tôt (`data-fixed-rows`, largeur nulle) et une étagère ne doit jamais rester invisible.
- ⚠️ **`visibility` et non `display:none`** : le re-packing mesure des `offsetWidth` de livres, tous nuls dans un conteneur non rendu — le voile s'annulerait lui-même.
- **Gate `.pf-shelves-js`** posée par un **script inline en tête de conteneur** (`document.currentScript.parentNode`, idiome de `.pf-cat-js`), exécuté par le parseur donc **avant le premier paint** — `bookshelf.js` est en pied de page, une classe posée par lui arriverait après la peinture. Sans JS la classe n'existe pas : l'étagère s'affiche normalement, à sa répartition théorique. Un `setTimeout` de 1,5 s dans ce primer est le filet du cas inverse (classe posée mais `bookshelf.js` jamais exécuté — asset manquant après un déploiement partiel) : l'étagère se dévoile quand même.
- **Inerte sur les swaps AJAX** (catalogue, bascule covers/spines, signets) : `innerHTML` n'exécute pas les scripts → pas de gate, donc pas de voile — et c'est correct, l'appelant rappelant `init()` dans **la même tâche** que l'insertion, il n'y a aucune peinture intermédiaire à masquer.
- **Vérifié** (headless, sonde `requestAnimationFrame` comptant les images où une étagère est visible ET débordante) : catalogue à **390 / 700 / 1400 px → 0 image**, contre 14 au contrôle ; JS coupé → étagère visible ; swap AJAX (recherche) → visible, `is-packed`, 0 débordement, et **pas** de `pf-shelves-js` (script non exécuté par `innerHTML`, comme prévu) ; fiche livre (hero, lui aussi en mode shelves) → `is-sized` + `is-packed`, livre visible aux deux largeurs.

⚠️ **Lectures et écritures DOM strictement séparées dans `repackShelves()` et `fitBookshelf()`.** Lire une géométrie (`offsetWidth`/`offsetHeight`) juste après avoir touché au DOM force un recalcul de layout immédiat. Ces deux fonctions le faisaient **par livre** (mesure de hauteur intercalée dans la boucle de déplacement) et **par rayon** (`--shelf-inner` écrite entre deux mesures) : sur le catalogue (146 livres, 78 rangées), la reconstruction coûtait **~950 ms** de main-thread — une long-task de 1156 ms que le voile ne faisait que **masquer**. Réécrites en passes séparées : **~35 ms**, et le voile tombe de **943 ms à 77 ms**. Ne pas ré-intercaler de mesure dans ces boucles. Depuis la suppression de `--shelf-inner` (cf. plus haut) il ne reste qu'une lecture — la passe `widths` de `repackShelves()`, faite **avant** la moindre écriture.

**Ce que la répartition PHP coûte vraiment** (question récurrente : « et si le serveur ne répartissait plus, en laissant tout au JS ? ») — **elle ne coûte rien et la retirer serait plus lent.** La boucle de `render_shelves()` mesure **0,0115 ms** pour 146 livres (arithmétique sur un tableau déjà en mémoire), à comparer au TTFB local de ~2,2 s ; le HTML produit est le même à ~40 wrappers `.pf-shelf` près (~3 Ko avant gzip sur 40 Ko). En face, partir d'une rangée unique est le **pire cas** du re-packing (chaque livre à déplacer, chaque rayon à créer), là où une répartition serveur déjà proche laisse souvent le court-circuit `same` sortir sans toucher au DOM. Le levier de vitesse n'est pas là mais dans le TTFB (cf. mémoire `performance_optimization`).

**Variable CSS globale partagée :**
- `--pf-sticky-offset` — bord bas du header collant (`#masthead`, cf. « Header collant ») ou de la barre d'admin, en pixels. Calculée et tenue à jour par `assets/js/recherche-globale.js` (chargé sur toutes les pages) au **DOMContentLoaded / resize / orientationchange / load — PAS au scroll** (+ `window.pfRefreshStickyOffset` pour le bandeau bêta, cf. section dédiée). `#masthead` étant en `position: sticky`, son bord bas vaut la même chose à l'arrêt et défilé : **une seule mesure, juste à tout moment**. C'est ce qui a permis de retirer le rattrapage « en-tête défilé au-dessus du viewport », que réclamait le sticky JS de Kadence (après un rechargement à scroll restauré, il n'avait pas encore re-fixé le header, la mesure tombait à 0 et les barres sticky se collaient derrière lui). Recalculer au scroll ne ferait que réécrire la même valeur, sauf sur iOS où `getBoundingClientRect()` (relatif au viewport **visuel**) suit le repli de la barre Safari → les éléments calés dessus (hero en `svh`, barres sticky) sauteraient. Seul écart assumé : barre d'admin WP en mobile (`position:absolute`, défile) → offset figé ~46px trop haut pour un admin connecté sur téléphone, sans effet visiteur. Les autres scripts (`catalogue.js`, `recherche-auteurs.js`, `accueil.js`) et les CSS (`catalogue.css`, `recherche-auteurs.css`, `accueil.css`) la consomment sans la recalculer. **Défaut CSS `:root` : `80px`** (« en attendant » le calcul JS ; le primer inline de `front-page.php`/`section-nav.php` pose la vraie valeur avant le premier paint sur ces pages). Le hero d'accueil fait `calc(100svh - var(--pf-sticky-offset))` : `svh` (≠ `dvh`) le rend stable face au repli de la barre iOS.

**Tailles d'image servies (perf) :** l'étagère **générique** (catalogue ~300 livres, accueil, livres associés…) sert deux sous-tailles dédiées, **non-crop** (ratio préservé), enregistrées par `register_image_sizes()` (`add_image_size`, hook `after_setup_theme`) et choisies dans `prepare_books()` selon `$is_hero` :

| Contexte | Couverture | Dos |
|---|---|---|
| Étagère générique | `pf-shelf-cover` (400×600) | `pf-shelf-spine` (300×760) |
| **Mode héros** (fiche livre, livre affiché bien plus grand) | `medium_large` (768) | `large` (1024) |

Les dos étant très étroits et hauts, c'est la **hauteur** qui contraint (760), la largeur suit le ratio (~30-90px) → poids minimal. Gain mesuré : couvertures d'étagère ≈ **17 % du poids** de `medium_large` (l'ancien `medium_large` retombait même sur l'original plein format quand l'upload faisait < 768px de large). ⚠️ **Gotcha** : `wp_get_attachment_image_url()` sur une sous-taille **non encore générée** retombe silencieusement sur l'**original plein format** (régression) → toute image déjà en médiathèque doit être régénérée après enregistrement d'une nouvelle taille (`wp_update_image_subsizes()` par pièce jointe, ou `wp media regenerate`). Les futurs imports les génèrent d'office. Le rendu (dimensions `width`/`height` dérivées des mm) est inchangé — seule la résolution source baisse.

The bookshelf design is functional but not final — further visual refinement is planned.

## PDF Catalog feature

The PDF catalogue list is fully admin-editable: a repeater field `catalogues` (SCF field group `group_6a4ba1e58c0bd`, "Menu déroulant Catalogues PDF", `lien` is a **text** field — not `url`, to allow root-relative paths like `/catalogue.pdf`) is attached to the Catalogue page (WordPress page ID 8 = `wc_get_page_id('shop')`). Each row has a label (`libelle`), an optional path/link (`lien`), and an optional uploaded PDF (`fichier`, attachment ID):
- **`fichier` + `lien` both set** → `lien` becomes the public virtual path that serves that exact file (dynamic rewrite rule, independent of the file's real media-library URL).
- **`lien` only** → used verbatim as the href (arbitrary external/absolute URL, no file served by this site).
- **`fichier` only** → href = the file's native media-library URL.

- **Admin UI:** WooCommerce → Catalogues PDF (`inc/catalogues.php`, slug `passiflore-catalogue`) renders the *native* SCF form for that field group via `acf_form()`/`acf_form_head()` (SCF's public form-rendering API — still `acf_`-prefixed for compatibility) instead of a hand-rolled form. `acf_form_head()` is hooked on `load-{$hook_suffix}` (must run before any HTML output, since it handles the POST save + redirect).
- **Réécriture dynamique :** pour chaque ligne fichier+lien, `passiflore_get_pdf_catalogue_rows()` calcule un chemin normalisé et `add_rewrite_rule()` (hook `init`, position `'top'`) le mappe vers `index.php?pf_catalogue_pdf=<attachment_id>` ; `template_redirect` sert le fichier via `readfile()`. ⚠️ Le cœur de WordPress (`WP_Rewrite::wp_rewrite_rules()`) ne relit **jamais en direct** les règles ajoutées par `add_rewrite_rule()` — il se contente du cache en base (option `rewrite_rules`) tant qu'il existe, sinon une URL modifiée/ajoutée redirige silencieusement vers l'accueil au lieu de 404 ou de servir le fichier. `acf/save_post` (scoping sur l'ID de la page Catalogue, priorité 20) appelle donc `flush_rewrite_rules()` à chaque enregistrement du repeater.
- **Front-end:** `passiflore_get_pdf_catalogues()` (`inc/catalogues.php`) reads the repeater and returns a normalized `[{libelle, url}, …]` list; `inc/class-catalogue.php` (`render_top_bar()`) loops over it to render the "Catalogues PDF" dropdown, hiding the whole block when the list is empty.

### Tarif d'expédition réduit au-delà d'un seuil (`inc/shipping.php`)

Réduit le forfait d'expédition d'une méthode « Forfait » (WooCommerce `flat_rate`) une fois un montant de commande atteint. **Réglé par instance de méthode**, directement dans la popup **« Configurer forfait »** d'une zone (WooCommerce → Réglages → Expédition → Zones d'expédition) — pas d'onglet global.

- **Deux champs ajoutés à la popup** via `woocommerce_shipping_instance_form_fields_flat_rate`, insérés juste après le champ natif « Coût » : `pf_seuil` (seuil € TTC) et `pf_cout_reduit` (forfait à partir du seuil ; vide = gratuit). Sauvegardés par WooCommerce dans l'option d'instance `woocommerce_flat_rate_{instance_id}_settings`.
- **Application** : `woocommerce_package_rates` (prio 100) parcourt les tarifs `flat_rate`, lit les réglages de **chaque** instance (`get_option`), et si `pf_seuil > 0` et `WC()->cart->get_displayed_subtotal()` (sous-total **TTC affiché**) ≥ seuil → `set_cost( pf_cout_reduit )` (+ recalcul TVA si la méthode est taxable). Seuil vide/absent → aucune réduction. Valeurs FR à virgule décimale acceptées.
- **Migration unique** (`admin_init`, flag `pf_shipping_seuil_migrated`) : reporte l'ancien réglage **global** (onglet « Tarif réduit » supprimé) dans les instances 1 (Point relais, 0,01 €) et 2 (Livraison à domicile, 2,00 €) de la zone National, seuil 35 € — préserve le comportement à l'identique et pré-remplit la popup. Défauts repris de l'ancien code si l'option globale n'avait jamais été enregistrée.

**Recalcul de la livraison au changement de pays — checkout en blocs** (`assets/js/checkout-shipping-country.js`, enqueué sur `is_checkout()` avec dép. `wp-data`) : contourne un **bug WooCommerce Blocks** (constaté en 10.6.1) — changer le `<select>` « Pays/Région » de l'adresse met à jour l'état interne (`wc/store/cart`) mais **ne déclenche pas** le push Store API qui recalcule les tarifs d'expédition (contrairement aux champs texte code postal/ville). Résultat sans correctif : le tarif reste celui du pays précédent tant qu'aucun champ texte n'est ré-édité. Le script écoute le `change` sur tout `<select …-country>` et, après un court debounce (300 ms, le temps que le bloc mette à jour le store avec le nouveau pays), rappelle `wp.data.dispatch('wc/store/cart').updateCustomerData({billing_address, shipping_address})` avec l'adresse complète relue du store → force le push et rafraîchit « Options de livraison » + total. Idempotent (un recalcul de plus si le bloc finit par pousser seul est inoffensif), try/catch silencieux (ne jamais casser le tunnel). Vérifié headless (puppeteer-core + Chrome système) : FR ↔ BE/DE bascule bien 0,01/2,00 € ↔ 8,00 €.

## Gotcha — guillemets typographiques dans les fichiers PHP

**Problème récurrent :** l'outil Edit introduit parfois des guillemets typographiques Unicode (`'` U+2018, `'` U+2019, `„` U+201E) à la place des apostrophes ASCII (`'` 0x27) dans le code PHP. PHP ne reconnaît pas ces caractères comme délimiteurs de chaîne, ce qui provoque une erreur de syntaxe fatale.

**Symptôme :** `Parse error: syntax error, unexpected identifier 'xxx'` sur une ligne qui contient une chaîne PHP `'...'` — PHP voit le contenu de la chaîne comme un identifiant nu parce que le délimiteur ouvrant n'est pas ASCII.

**Vérification :** après tout Edit sur un fichier PHP, lancer :
```
"/Users/loicrobin/Library/Application Support/Local/lightning-services/php-8.2.29+0/bin/darwin-arm64/bin/php" -l "chemin/vers/fichier.php"
```

**Correction si détectée :** utiliser Python pour remplacer les bytes exacts :
```python
import re
path = "chemin/vers/fichier.php"
data = open(path, 'rb').read()
data = data.replace(b'\xe2\x80\x98', b"'")           # U+2018 → ASCII '
data = re.sub(rb'\xe2\x80\x99(?=[;,)\].\'\\s])', b"'", data)  # U+2019 closing → ASCII '
open(path, 'wb').write(data)
```
Vérifier ensuite que les U+2019 légitimes (apostrophes françaises dans du contenu de chaîne, ex. `l'événement`) ne sont pas touchés.

**Règle :** après chaque Edit sur un fichier PHP, faire un `php -l` systématique.

## Gotcha — ne jamais tuer Chrome globalement pendant les tests visuels

Les vérifications visuelles lancent des instances **Chrome headless** (CDP / `--screenshot`). **Ne JAMAIS** faire `pkill`/`killall` sur « Google Chrome » (ni aucun motif large) : le **navigateur GUI de l'utilisateur** — où il regarde le site en local — tourne sous le même nom et serait tué, l'obligeant à tout relancer. Chaque instance de test doit utiliser un `--user-data-dir` **et** un `--remote-debugging-port` **uniques**, et n'être arrêtée que par son propre lanceur (le script node tue le seul process enfant qu'il a spawné, par son PID). Pas de nettoyage « au nom » ; les instances headless se terminent d'elles-mêmes (kill ciblé du PID par le lanceur, ou `--virtual-time-budget`). Un `--user-data-dir` unique par run suffit à éviter tout conflit de profil/port, donc aucun `pkill` préalable n'est nécessaire.

## Sécurité AJAX — politique de nonce

**Endpoints publics en lecture seule = pas de nonce** (choix acté). Un nonce WordPress n'a de valeur que pour la protection CSRF d'une action **qui modifie un état au nom d'un utilisateur connecté** ; sur un endpoint `nopriv` qui ne fait que **lire des données publiques**, il n'apporte aucune sécurité (pour un visiteur déconnecté, `wp_create_nonce` produit même un jeton partagé tournant toutes les 12 h) et provoque un **403 sur un onglet resté ouvert au-delà de la durée de vie du nonce** (12–24 h). Ces endpoints n'appellent donc **pas** `check_ajax_referer` et n'émettent pas de nonce : `pf_global_search`, `pf_recherche_auteurs`, `pf_catalogue(_filter)`, `pf_events_feed`, `pf_events_search`, `pf_events_map_search`. **Ne pas “réparer” en re-ajoutant un nonce.**

**Endpoints à état = nonce conservé + dégradation gracieuse.** Ceux qui écrivent (panier `pf_numerique_*`, newsletter, avis `pf_avis_*`, liste de lecture / signets `pf_reading_list_toggle`, suppressions, sauvegardes admin) **gardent** leur nonce. Pour éviter l'échec silencieux d'un 403, leur JS détecte `response.status === 403` **avant** `.json()` et appelle `window.pfSessionExpired({ mode })` (voir `assets/js/pf-session-toast.js`) : mode `'reload'` pour les actions pures (panier, suppressions), `'confirm'` là où un auto-reload perdrait une saisie ou une position de navigation (avis, newsletter, liste de lecture, signets). Le sondage de fond du panier, lui, avale le 403 silencieusement (pas d'action utilisateur → pas de toast).

## Karpathy Skills - Build Commands

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.
