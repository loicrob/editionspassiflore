# Audit CSS & Stratégie Design System — Éditions Passiflore

> Étape 1 (Audit & Stratégie) de la consolidation des CSS locaux en design system unifié.
> **Statut : arbitrages §3 tous validés le 2026-07-02 (suggestions acceptées).** Exécution selon §6.
> Complète `design-system.md` (décisions de 2026-06) — ce document est l'état des lieux au 2026-07-02.

## Contexte

16 fichiers CSS custom (~7 300 lignes) : `style.css` (928 l.) + 15 fichiers dans `assets/css/`. Objectif : harmoniser, alléger, rendre maintenable — **zéro régression visuelle**, en respectant la palette Kadence (Customizer) et en préparant des règles CLAUDE.md pour que les futurs agents n'écrivent plus de CSS local redondant.

## 0. Constat de départ — la situation est meilleure qu'annoncé

L'hypothèse « quelques variables globales sans systématique » est **périmée**. L'état réel :

- **`style.css` contient déjà un vrai design system** (~500 lignes) : tokens complets (couleurs sémantiques `--pf-*` → palette Kadence, échelle typo `--pf-text-*`, interlignes, graisses, espacement `--pf-space-1…20`, 4 radius, 2 ombres, focus rings, transitions) **et** des composants globaux : `.pf-btn` + variantes, `.pf-card` + famille, `.pf-badge`, `.pf-search`, `.pf-switch`, `.pf-dropdown`, `.pf-sticky-bar`, `.pf-hscroll`, `.pf-avis-reponse`, base formulaires, base `shop_table`, défauts `h1–h6`, `.pf-titre-1/2/3`, `.pf-label`.
- **`docs/design-system.md` existe** (2026-06-22) avec des décisions déjà actées (polices serif/sans, radius 3px, règles de refactor boutons B.5, règle espacement B.6) et un plan d'exécution en 5 étapes. On est **au milieu de son étape 4** (refactor fichier par fichier).
- La **stratégie Kadence est déjà en place et bonne** : couleur des boutons natifs pilotée via les variables `--global-palette-btn-*` redéfinies avec `!important` sur la *définition* (bat le CSS inline du Customizer sans rigidifier la cascade) ; échelle d'espacement Gutenberg `--global-*-spacing` câblée sur `--pf-space-*`. Les admins gardent la main via la palette du Customizer.
- **Migration inégale selon les fichiers** (usages de `var(--pf-…)` / hex en dur) :

| Fichier | Tokens | Hex en dur | État |

La tâche n'est donc **pas** de créer un design system, mais de **finir la migration** vers celui qui existe, d'extraire ~6 composants encore dupliqués, et de trancher les dérives listées ci-dessous.

## 1. Incohérences de gouvernance (à corriger avant tout refactor)

1. **`palette10` : la base ≠ la doc.** Le Customizer (vérifié en BD, `second-palette` active) contient `palette10 = #e0d8cc`, mais CLAUDE.md et design-system.md documentent `#D9C8B0`. Conséquence : **`--pf-border` (= palette10) et `--pf-border-light` (= `#e0d8cc` en dur) sont aujourd'hui identiques** — deux tokens pour une seule couleur. Et les `#D9C8B0` en dur (newsletter.css, badge « attente » de mes-avis.css) rendent un sable **plus foncé** que le token.
2. **`design-system.md` partiellement périmé** : §A.0 (« couches vides ») n'est plus vrai ; §A.1 (corriger palette1) est **fait** ; §B.5 dit `--pf-btn-weight: 600` mais style.css a `400` ; §B.7 ne liste que 2 radius (il y en a 4) ; §B.1 table des rôles palette obsolète (7=or, 8/9 inversés).
3. **CLAUDE.md incomplet** : liste 9 fichiers CSS sur 16 (manquent account, cart, checkout, mes-avis, newsletter, recherche-globale, reading-list) et documente le mauvais hex palette10.
4. Le commentaire de style.css annonce une variante `.pf-switch--solid` **qui n'existe pas** (le « solid » vit en fait dans events.css sous un autre nom, cf. §2.2).

## 2. Doublons fonctionnels — composants candidats à la globalisation

### 2.1 Contrôles du catalogue ≈ composants globaux (migration à moitié faite) — priorité 1

Le markup PHP porte **déjà la double classe** (`pf-cat-trigger pf-dropdown__trigger`, `pf-cat-display pf-switch`, `pf-switch__btn` — vérifié dans `inc/class-catalogue.php:274-567`), mais catalogue.css **re-déclare des valeurs identiques** à celles du composant global (padding 8px 12px, bordure `--pf-border-light`, radius 6px, fond crème, survol red-soft). Action : purger de catalogue.css les déclarations redondantes, ne garder que les vrais deltas (hauteur `--pf-cat-control-h` 34/38/40px, font-size 13/14/15px, collapse du tri, paire univers/collection). La recherche globale (`inc/class-recherche-globale.php`) montre le modèle cible : composant global + fines surcharges locales.

De même `.pf-cat-search` (38px, radius 6px) réimplémente `.pf-search` (44px, radius 8px) — le global expose déjà ses variables de géométrie (`--search-h`, `--search-icon`, `--search-inset`…, cf. la variante `.pf-search--sm`). Candidat : adosser `.pf-cat-search` à `.pf-search` en surchargeant les variables ; les comportements bespoke (expansion au focus, collapse du tri) restent locaux.

### 2.2 Switch de vue TEC = deuxième composant switch — priorité 1

`tribe/events/v2/components/events-bar/views.php` utilise `.pf-view-switch` (classe distincte), stylée dans events.css avec la même recette que `.pf-switch` mais un actif « aplat rouge ». Candidat : créer `.pf-switch--solid` dans style.css (le commentaire l'annonce déjà), faire porter `pf-switch pf-switch--solid` au markup TEC, et ne garder dans events.css que les shims de spécificité anti-TEC/Kadence (`display:flex !important` etc., nécessaires).

### 2.3 Panneau encadré « .pf-panel » — priorité 1 (nouveau composant)

Même recette répétée ~8 fois : `border: 1px solid var(--pf-border-light)` + `border-radius: var(--pf-radius-lg)` + fond `--pf-surface` ou `--pf-surface-alt` + padding ≈ 1.2rem :
- cart.css `.cart_totals` (1.2rem 1.4rem), checkout.css `#order_review` (1.2rem 1.4rem), `#payment`, `.woocommerce-order-overview` (1rem 1.4rem)
- account.css nav MyAccount, panneaux `#customer_login .col-1/.col-2` (clamp), `.pf-account-danger` (variante bord accent + fond red-soft)
- mes-avis.css `.pf-avis-card` (1.1rem 1.25rem)

Candidat : `.pf-panel` (+ `--alt` fond crème, `--danger` bord accent) dans style.css ; les pages ne gardent que leurs paddings de cellules (densités voulues, décision design-system.md conservée).

### 2.4 Citation à filet gauche « .pf-quote » — priorité 2

`.bs-avis-item` (book-single.css : fond surface-alt, `border-left: 3px solid var(--pf-border)`, radius `0 3px 3px 0`) ≈ `.pf-avis-reponse` (style.css : idem avec filet accent). Candidat : base commune `.pf-quote` + modificateur de couleur de filet.

### 2.5 Notices de statut « .pf-notice » — priorité 2

Trois implémentations locales : `.bs-avis-erreur` (fond `#fdecea`, texte `#8a1c25`, filet accent), `.pf-newsletter__message.is-success` (`#1a7a4a`) / `.is-error` (`#a0212c`). Candidat : `.pf-notice--error/--success` globales + tokens statut (cf. arbitrage n°8).

### 2.6 Bouton rond icône « .pf-roundbtn » — priorité 2

Le CLAUDE.md le dit lui-même : les boutons ronds des événements sont « calqués sur le bouton de fermeture de la recherche globale ». Occurrences : `.pf-ev-roundbtn` (40px, fond accent, icône crème, events-infinite.css), bouton fermeture recherche globale (`--pf-gs-btn-size: 40px`), `.pf-ev-tofuture`. Candidat : `.pf-roundbtn` global (40px, accent, hover accent-dark, `!important` conservés car nécessaires contre `.entry-content button`). Restent locaux : toolbar flipbook (thème sombre bespoke), flèches Splide (2.2rem, lib embarquée), boutons effacer ×(22/26px, déjà dans `.pf-search`).

### 2.7 Titre de section avec trait + lien-flèche (accueil) — priorité 2

accueil.css implémente **deux fois à l'identique** le trait ornemental (`::after` 2.5rem × 2px accent : `.pf-section-titre:not(:has(a))::after` l.650 et `.pf-etagere-titre:not(:has(a))::after` l.920) et deux fois le titre-lien avec flèche `➜` translatée au survol. Candidat : un composant `.pf-section-header` (ou modificateur de `.pf-titre-*`) dans style.css — c'est LE motif « titre de section » que l'utilisateur veut harmoniser site-wide.

### 2.8 Spinners — priorité 3

`pf-ev-spin` (0.7s), `bs-tb-spin` (0.75s) : mêmes keyframes. Candidat : un `.pf-spinner` + `@keyframes pf-spin` globaux (0.7s ; l'écart 0.75→0.7s est imperceptible).

### 2.9 Ombres à tokeniser — priorité 2

Ombres « détachées » quasi identiques mais toutes différentes :
- **stuck** (élément sticky collé) : style.css `.pf-sticky-bar.is-stuck` (composite `0 1px 0…, 0 12px 24px -16px…`), accueil `.pf-header-stuck` (`0 2px 8px rgba(0,0,0,.04)` + clip-path), events séparateur de mois (`0 8px 12px -8px rgba(94,82,77,.3)`)
- **flottant** (menus/pop) : `.pf-dropdown__menu` (`0 10px 24px -8px rgba(94,82,77,.18)`), résultats recherche globale (`0 8px 24px rgba(0,0,0,.12)`), `.pf-ev-roundbtn` (`0 4px 14px -4px rgba(94,82,77,.4)`)

Candidat : `--pf-shadow-stuck` et `--pf-shadow-float` (cf. arbitrage n°9). Les ombres 3D de bookshelf.css restent hors périmètre.

### 2.10 newsletter.css — retokenisation complète — priorité 1

0 token, 20 hex (tous mappables : #c62836→accent, #a0212c→accent-dark, #FCFBF7→surface-alt, #D9C8B0→border, #5e524d→text, #1a1615→heading), radius 4px hors échelle, focus ring 2px non conforme, bouton hors `.pf-btn`. Chargé sur **toutes** les pages → c'est du CSS global de fait. À aligner intégralement sur les tokens/composants existants (règles B.5/B.6 du design-system.md).

## 4. Ce qui reste local (justifié — ne pas globaliser)

- **bookshelf.css** : moteur 3D (planches, perspective, dos, chevalets, variables posées par JS `--book-h`/`--spine-w`/…). Les `--plank-color-*`/`--wall-color`/`--frame-color` sont des « matériaux », pas des tokens de marque (décision déjà actée dans CLAUDE.md).
- **events.css** : mécanique sticky TEC (header smart-hide, séparateurs de mois full-bleed, « push »), ~30 `!important` **nécessaires** contre la spécificité TEC — à conserver tels quels, en consommant les tokens.
- **accueil.css** : héro (typage animé, catégories, scroll-CTA), animations d'étagère (`pf-cover-settle`…), section contact.
- **catalogue.css** : comportement de barre (collapse du tri au focus, fondus mask-image, chips), une fois purgé des doublons §2.1.
- **book-single.css** : hero grid, flipbook (overlay + toolbar sombre : palette bespoke assumée), sectionnav.
- **events-infinite.css** : mécanique du scroll infini (une fois `.pf-roundbtn`/`.pf-spinner` extraits).
- **Paddings de cellules `shop_table`** par page (densités voulues — décision design-system.md).

## 5. Règles à inscrire dans CLAUDE.md (futur-proofing)

À ajouter (section « CSS — Design System ») une fois le refactor fait :

1. **Jamais de nouvelle valeur en dur** : couleur → `--pf-*` (ou `--global-palette*` via un token), taille structurelle rem → `--pf-space-*`, radius → un des 4 tokens, ombre → `--pf-shadow*`, focus → `--pf-focus-ring*`. Les alphas dérivés → `color-mix()` sur un token. Exceptions autorisées : valeurs en `em` relatives au texte, micro-géométrie de composant (documentée par une var locale commentée).
2. **Avant d'écrire du CSS : lire les composants de style.css** (`.pf-btn`, `.pf-card`, `.pf-panel`, `.pf-badge`, `.pf-search`, `.pf-switch`, `.pf-dropdown`, `.pf-sticky-bar`, `.pf-quote`, `.pf-notice`, `.pf-roundbtn`, `.pf-spinner`, `.pf-label`…) et `docs/design-system.md`. Un motif présent sur ≥ 2 pages appartient à style.css, préfixe `.pf-` obligatoire.
3. **Un CSS de page ne contient que** : layout propre à la page, comportements bespoke, shims de spécificité anti-plugin. Toute règle « apparence d'un composant » remonte dans style.css.
4. **Boutons** (règle B.5 existante) : markup custom → classes `.pf-btn .pf-btn--…` ; boutons WooCommerce/plugins → garder le sélecteur, pointer les valeurs sur les tokens. États `:hover/:focus/:active/:disabled` obligatoires.
5. **Kadence** : ne jamais surcharger une couleur de bouton natif par des règles — passer par les variables `--global-palette-btn-*` (motif existant en `:root`). `!important` interdit entre fichiers du thème enfant ; autorisé uniquement contre TEC/Woo/Kadence/Customizer (et de préférence sur une *définition de variable*).
6. **Breakpoints** : 480 / 768 / 1024 (`max-width: 767px` ↔ `min-width: 768px`) ; exceptions documentées (600 auteur, 781 TEC).
7. **Hauteur de contrôle** : variante de taille via `--pf-control-h` (et `--search-*`), pas de nouvelles hauteurs codées en dur.
8. **Après tout ajout de token/composant** : mettre à jour `docs/design-system.md` ; vérification visuelle (captures) avant/après sur les pages touchées.

## 6. Stratégie d'exécution proposée (étapes suivantes, hors périmètre de cette tâche)

4. **Purge fichier par fichier** (du plus rentable au moins) : newsletter → catalogue (§2.1) → events (§2.2, roundbtn/spinner) → accueil (§2.7, doublons de titres) → account/cart/checkout/mes-avis (`.pf-panel`) → book-single (`.pf-quote`, `.pf-notice`).
